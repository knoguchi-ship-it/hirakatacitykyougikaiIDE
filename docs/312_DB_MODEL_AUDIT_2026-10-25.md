# DB モデルの整合性監査（2026-10-25）

スキーマを変える前に、ER 図を作り直し、DB モデルに矛盾が無いかを確かめた（operator 指示）。
以後、表・列・関係を変えるときは `npm run audit:db-model` を通す（prerelease に組み込み済み）。

## 1. 何を突き合わせるか

モデルの情報は 7 か所にある。1 か所だけ直すと、削除の連動から漏れる・ER に関係が出ない・テストデータが残る、が気づかれずに起きる。

| 情報 | 場所 | 既存の検査 |
|---|---|---|
| 列の正本 | gas-src `テーブル定義` | — |
| 型・キー・関係 | `docs/er-metadata.json` | `test:er-sync`（列・表の存在） |
| DB が守らない ID 参照 | `DB_STATE_ID_REFERENCES_` | `test:db-state` |
| 入力規則（マスタの選択肢） | `入力規則定義` | `test:db-relations` |
| 削除でアーカイブへ移す表 | `ARCHIVE_SOURCE_TABLES` | `test:db-relations`（列の形） |
| 削除の連動で見る列 | `getCascadeMatchers_` | — |
| テストデータ削除の分類 | `TEST_DATA_PURGE_TABLE_POLICY` | `test:test-data-purge`（分類の有無） |

`audit:db-model` が新しく見る観点:

1. 「〜ID」の列に関係があるか（主キー・意図して関係を持たない列は理由つきの例外）
2. 関係の列が表にあるか（関係の名前の注記 `会員ID(v360 2-FK)` は括弧の前を列名とする）
3. ER の FK 表示と関係が一致するか
4. 会員・職員を参照する表が、アーカイブ・削除の連動・テストデータ削除の 3 つにそろって入っているか
5. 「会員ID か 職員ID のどちらか」の表（`OFFICER_PERSON_TABLES_`）は両方とも任意の関係か
6. `DB_STATE_ID_REFERENCES_` と ER の関係が一致するか
7. 入力規則が ER の関係にあるか
8. 数字だけの文字列を入れる列（電話・FAX・郵便番号・「〜番号」・ログインID・金融機関 / 支店コード）が `TEXT_FORMAT_COLUMNS_`（書式なしテキスト）にあるか。無いと先頭の 0 が消える（2026-10-25 追加・`docs/311` §5.5）

監査そのものが効くことは、`T_支払い.職員ID → T_事業所職員` の関係を一時的に消して 3 つの観点（関係なし・FK 表示・ID 参照の一覧）で落ちることで確かめた。

## 2. 結果

表 45（アーカイブ除く）／ 関係 70 ／ ID 参照 30 ／ アーカイブ対象 13。**直したあとの食い違い 0。**

| 見つけたもの | 判断 | 対応 |
|---|---|---|
| `T_研修申込.照合会員ID` / `照合職員ID` に関係があるのに FK 表示でない | **ER の注記の誤り** | `er-metadata.json` を FK に |
| 同じ 2 列を削除の連動が見ない | **意図どおり**。申込は外部申込者のもので、照合した時点の記録。名簿の表示ラベルにだけ使い、参照先が無くなっても害が無い | 理由つきの例外 |
| 「〜ID」なのに関係が無い 9 列（ログインID ×2・申込者ID・受信者ID・対象レコードID・人物統合ログの新旧 4 列） | **意図どおり**。ログインID は自然キー、申込者ID・受信者ID・対象レコードID は種別で参照先が変わる多態参照、人物統合ログは過去の ID の記録 | 理由つきの例外 |
| `T_認証アカウント.会員ID` が必須（XOR の検査で拾った） | **監査の誤り**。事業所職員のアカウントも事業所の会員ID を必ず持つ（`createPasswordAuthRow_` に会員ID と職員ID の両方を渡す）。XOR ではない | XOR の検査を役員まわり 4 表に限定 |

## 3. 文書の食い違い（同時に直した）

| 文書 | 食い違い | 直したこと |
|---|---|---|
| `docs/spec/05_DATA_IF.md` §2.3 | `T_認証アカウント` を「会員ID・職員ID（どちらか一方が入る）」としていた | 会員ID は必ず入る。職員のアカウントは事業所の会員ID ＋ 職員ID |
| 同 | 役員まわりの表を「`T_会員` / 会員ID」だけとしていた。`T_支払い` が無い | 4 表とも会員ID か 職員ID のどちらか一方 |
| `docs/03_DATA_MODEL.md` 冒頭・§9 | スキーマの版が v376.52 で止まり、v376.65 / v376.71 / v376.125 が履歴に無かった | 現行版と 3 版分の履歴を追記 |
| 同 §4.12 | XOR の表が 3 つ（`T_支払い` が無い）・紐づけ変更は「口座も移す」だけ | 4 表・人単位の付け替え・共通関数・認証アカウントは XOR でないこと |
| 同（人物の統合） | `T_支払い` は会員同士のときだけ移す | 役員まわり 4 表として常に移す |

## 4. 次のスキーマ変更（公開ポータルの案内文の定型文）

`T_画面文テンプレート`（仮）を足すときも、この監査を通す。会員・職員とは結び付かないので、
`TEST_DATA_PURGE_TABLE_POLICY` は `NONE`、アーカイブ・削除の連動の対象外になる見込み。
