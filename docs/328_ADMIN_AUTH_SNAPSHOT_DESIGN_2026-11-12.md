## 1. 何が起きているか（事実）

| 事実 | 出典 |

| `T_管理者Googleホワイトリスト` は **4 行**、`T_認証アカウント` は **362 行（削除 15）×19 列** | 本番の件数（`describeDatabaseState_LOG`・2026-11-12） |

**原因は管理者の数ではなく作り**: 管理者の認証が会員全体の認証表に寄りかかり、1 行のために全行を読み、上限を超えるものをキャッシュしようとしている。

## 2. 目的と、やらないこと

**目的**
1. 管理 API の認証で、**ふだんはスプレッドシートに触れない**（プロパティ 1 回 5〜50 ms）。
2. 会員のパスワードハッシュ・ソルトを、管理者の認証で**読まない・どこにも置かない**。
3. 管理者を外したときの反映を**今より遅くしない**（今は最大 5 分）。
4. 応答（セッションの中身）・エラー文・ログイン履歴の記録を**今と同じにする**（画面・クライアントは変えない）。

**やらないこと（範囲外）**
- 紐付けの正本を変える（直し方 B）。TRD §1.4「現在の紐付けは `T_認証アカウント` の行が正本」は維持する。
- 判定の条件を変える。**今の判定は認証行の `アカウント有効フラグ`・`ロック状態` を見ていない**（削除フラグだけ）。気づいたが、挙動を変えるので本件では変えない（§9 に記録）。
- ロール（`T_権限ロール`）の読み方。`getRoleByIdCached_`（キャッシュ・1 回 16〜35 ms）のまま。
- 会員・公開プロジェクト。管理プロジェクトのプロパティにだけ置く（3 境界でキャッシュ・プロパティを共有しない）。

## 3. 完成品（管理者認証のスナップショット）

**置き場所**: 管理プロジェクトのスクリプトプロパティ、キー `ADMIN_AUTH_SNAPSHOT_V1`。

```json
{
  "v": 1,
  "builtAtMs": 1762920000000,
  "dbModifiedAtMs": 1762919990000,
  "admins": {
    "<Googleメール（小文字）>": {
      "status": "OK",
      "whitelistId": "WL-001",
      "permCode": "MASTER",
      "roleId": "ROLE-...",
      "authId": "AUTH-...",
      "roleCode": "...",
      "memberId": "...",
      "staffId": "...",
      "memberName": "..."
    }
  }
}
```

| 項目 | 作り方（いまの `checkAdminBySession_` と同じ規則） |
|---|---|
| 対象の行 | ホワイトリストのうち `削除フラグ` が偽かつ `有効フラグ` が真の行。**同じメールが複数ならシートの上の行**（今と同じ「最初に一致」） |
| `permCode` | `権限コード`。空なら `ADMIN` |
| `status` | `GENERAL`（権限コードが GENERAL）／`NO_AUTH_LINK`（紐付け認証IDの行が無い・削除済み）／`NO_MEMBER`（会員IDが空）／`OK`。判定の順も今と同じ |
| `authId` `roleCode` `staffId` | 紐付く認証行（`削除フラグ` が偽）の `認証ID` `システムロールコード` `職員ID` |
| `memberId` | 認証行の `会員ID`、空なら ホワイトリストの `紐付け会員ID`（今と同じ） |
| `memberName` | 職員IDがあれば `T_事業所職員` の姓名（無ければ氏名）、なければ `T_会員` の姓名（今と同じ順） |

- **入れないもの**: パスワードハッシュ・ソルト・ログイン失敗回数など、認証行の他の列。
- 大きさ: 1 人 約 300 文字。4 人で約 1.2 KB。**8,000 文字を超えたら保存しない**（プロパティの 1 値の上限 9 KB の手前）→ 毎回シートから作って答え、ログに出す（約 25 人を超えたとき。動くが遅い）。
- 個人情報（管理者のメール・氏名）を置くが、プロパティを読めるのはスクリプトの編集者だけで、その人は元々 DB 全体を読める（`docs/325` §3.3）。**ブラウザには一切渡らない。**

## 4. 読み方（要求のたび）

```
email = Session.getActiveUser().getEmail()        // 今と同じ。空なら拒否
snap  = getAdminAuthSnapshot_(ss)                 // §5
entry = snap.admins[email]
無い          → 失敗をログイン履歴に「ホワイトリスト未登録（セッション認証）」・拒否
GENERAL       → 失敗を記録「一般権限のため管理者ログイン不可」・拒否
NO_AUTH_LINK  → 失敗を記録「紐付け認証ID未整備（セッション認証）」・拒否
NO_MEMBER     → 失敗を記録「会員ID未紐付け（セッション認証）」・拒否
OK            → 表示名（masterLabel_）・ロール（getRoleByIdCached_）を足して、今と同じ形のセッションを返す
recordLogin   → 成功を記録（今と同じ）
```

エラー文・記録する理由の文言・認証IDは今と同じ。

## 5. 鮮度（いつ作り直すか）

| 条件 | 動き |
|---|---|
| プロパティが無い・JSON が壊れている・`v` が違う | **シートから作り直す**（正本で確かめる） |
| 作ってから **5 分**を超えた | 作り直す（**今のキャッシュの 5 分より古いもので通すことは無い**） |
| 直近 30 秒に確認済み（CacheService の印 `admin_auth_snap_ok_v1` = `builtAtMs`） | そのまま使う |
| それ以外 | DB の最終更新日時（Drive）を読む。`dbModifiedAtMs` 以下ならそのまま使い、印を 30 秒置く。**新しければ作り直す** |
| 最終更新日時が読めない（例外） | 作り直す（確かめられないときは正本へ） |
| 管理画面で権限・ロール・ホワイトリストを保存した | **その場でプロパティを消す**（`clearAdminPermissionCaches_`）→ 次の要求で作り直す |

- **作り直すとき、DB の最終更新日時はシートを読む前に取る**。読んでいる間に書かれても、次の確認で「新しい」と分かる。
- 作り直しはプロパティにしか書かない（DB に書かない）ので、自分の作り直しで最終更新日時が動いて作り直しが続くことは無い。
- 1 回の要求の DB への書き込み（ログイン履歴・監査ログ）は**ログ用スプレッドシート**へ行く（`getLogSs_`）。メインの DB の最終更新日時は動かない（2026-11-12 確認）。
- 同時に 2 つの要求が作り直しても、同じ中身を書くだけで害は無い。
- 印（30 秒）がキャッシュから消えても、最終更新日時を読み直すだけ（安全側）。

**反映までの時間**
- 管理画面での変更: **即時**（RD §12 の「即時無効化」を満たす）。
- それ以外（会員・公開での退会・紐付け変更、スプレッドシートの直接編集）: **最大 30 秒 ＋ Drive の最終更新日時の反映遅れ**。上限は 5 分（今と同じ）。
- **Drive の最終更新日時が書き込みからどれだけ遅れて変わるかは未検証**（`docs/325` §3.4-2）。計画の最初に、個人情報の無い一時スプレッドシートで計る（§8）。遅れが大きくても上限 5 分は守られる（最大経過時間で作り直すため）。

## 9. 記録（気づいたが本件で変えないこと）

- 管理者の判定は、紐付く認証行の `アカウント有効フラグ`・`ロック状態` を見ていない（削除フラグだけ）。会員側のログインを止めても、その人の管理者ログインは止まらない。
  **operator 決定（2026-11-12）: 管理者は権限の側で止める**（管理画面でホワイトリストから外す・無効にする・ロールを変える）。判定の条件は変えない。
  この経路は本設計で即時に反映される（§5）。参考: `ロック状態` を管理者の判定に入れると、CM 番号を知る第三者が会員ログインをわざと失敗させて管理者を締め出せる（ロックアウトによるサービス妨害）ので、入れない方が安全。
  残る穴: `saveAdminPermission_` は最後の MASTER を外す操作を止めない（既知・HANDOVER）。権限で止める運用を正式にするなら次に塞ぐ。
- ホワイトリストの読み（4 行）が 0.2〜0.9 秒の理由は未特定。この設計で普段の経路から消えるので、作り直しのときだけの費用になる。
