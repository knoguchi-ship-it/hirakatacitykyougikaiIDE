# Release State v342

Date: 2026-05-13
Status: production deployed

## Scope

- Hardened `writeSheetHeaders_` to perform name-based data-row migration when sheet
  headers diverge from the schema. Column insert / rename releases no longer leave
  data rows in their old column positions. This is the structural fix for the root
  cause of the 2026-05-12 schema-shift incident (`docs/204`).
- Added `auditDeleteFlagColumns_` as a read-only post-init sanity check. Walks every
  `T_*` table that defines `削除フラグ` and logs a warning when non-boolean values
  are present, surfacing any latent drift via Apps Script `Logger`.
- Documented the `initializeSchema_` ordering invariant directly above the function
  body (master sheets first, table-sheet ensure, then `normalizeTableColumns_`, then
  the new audit). v340 had already switched `createTableSheets_` → `ensureTableSheetsExist_`;
  v342 makes the rationale explicit so a future change does not regress.
- Updated `docs/09_DEPLOYMENT_POLICY.md` with a mandatory schema-migration release
  step: when `DB_SCHEMA_VERSION` changes or column structure changes, the deploy
  checklist now requires manual `runRebuildSchemaForV<N>` after admin push, plus a
  log inspection for `schema-drift suspected` / `schema drift detected` warnings.
- Bumped `DB_SCHEMA_VERSION` to `2026-05-13-schema-shift-guard-v1` so the first hit
  on any of the three Web Apps after deploy re-enters `initializeSchema_` once and
  exercises the new guard against the live production sheets.

## Behavioural notes

- The new `writeSheetHeaders_` migration path preserves existing data validation,
  formatting, and protections by performing the shift in place (it rewrites the
  data area only and clears trailing surplus columns). It does not use the
  temp-sheet swap pattern, which would have dropped sheet-level metadata.
- The first Web App request after deploy will re-run `initializeSchema_` because
  the cached `SCHEMA_INITIALIZED_VERSION_KEY` Script Property no longer matches
  `DB_SCHEMA_VERSION`. The audit logs are visible in the Apps Script editor under
  Executions for whichever project takes the first hit. The audit is read-only and
  fast (single column scan per `T_*` table).
- Public / member / admin all share the same DB spreadsheet, so the
  re-initialisation runs exactly once across the three Web Apps, gated by
  `LockService.getScriptLock` inside `initializeSchemaIfNeeded_`.
