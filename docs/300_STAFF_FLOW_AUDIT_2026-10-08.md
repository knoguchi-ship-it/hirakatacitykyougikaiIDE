## 2. 直した 4 件

### ★1 職員追加で認証アカウントが作られなかった（RD §224）

> 職員追加 → 職員レコードと**認証アカウントを作成**する

`addApprovedStaffMember_` は `T_事業所職員` に行を足すだけだった。
認証アカウントを作る経路は `adminIssueMemberCredential_`（**管理者が手で実行する操作**）しかなく、
通知メールの本文も実装側で `var saPassword = '事務局から別途通知';` となっていた。

**直し方**: `ensureStaffAuthAccount_` を新設し、職員行の作成に続けてアカウントを作る。
ログインIDは `generateCmBasedLoginId_` で採番（既存IDとの重複を見る）、パスワードは乱数、
**同じ職員の既存アカウントがあれば何もしない**（再承認で重複させない）。

> **通知は送らない。** operator の運用は「アカウントの発行だけして通知は流さない」
> （会員マイページを未開放のため）。本番の `STAFF_ADD_STAFF_EMAIL_ENABLED` は既に `false` で、
> 設定がそれを表現している。**コードには何も埋め込まない。**

### ★2 代表者への職員追加通知が一度も届いていなかった

```js
String(r['権限コード'] || '') === 'REPRESENTATIVE'   // 誤り
```

`T_事業所職員` に **`権限コード` という列は無い**（正しくは `職員権限コード`）。
この絞り込みは常に空を返し、`repStaffRow = null` → 代表者メール・代表者名が空 →
**`STAFF_ADD_REP_EMAIL_ENABLED = true` なのに通知が送られない**状態だった。

`権限コード` 自体は `T_管理者Googleホワイトリスト` の正しい列で、他 9 箇所の参照は妥当。
**誤りはこの 1 行だけだった。**

### ★3 職員の必須項目がサーバー側で検査されていなかった（BR-16）

必須検査は**姓・名だけ**で、セイ・メイ・メールアドレス・CM 番号は空でも職員行が作れた。
公開ポータルのフォームは 6 項目そろった行だけを送るが、**画面でしか守られていない**——
v376.110 で潰したのと同じ型。4 項目の検査を追加した。

### ★4 職員数上限に全体既定が効いていなかった（RD §136 / §205）

```js
var staffLimit = limitVal ? Number(limitVal) : 0;
if (staffLimit > 0) { … }     // 0 なら無制限
```

会員行の `職員数上限` が空の事業所では**上限が一切効かなかった**。
全体既定 `DEFAULT_BUSINESS_STAFF_LIMIT`（本番の現在値 10）を参照していなかった。
個別上限が未設定なら既定へ落ちるようにした。

## 3. 仕様を直した 1 件

### ★5 BR-02「代表者情報を会員レコードへ自動同期」

実装は v131 以降、事業所会員の `姓 / 名 / セイ / メイ / 介護支援専門員番号` を
**保存時に空へ揃えて**おり、本番の事業所会員 37 件すべてが空。**仕様と実装が正面から矛盾していた。**

**同期した場合に何が起きるかを、読み手をすべてたどって確認した。**

| 読み手 | 事業所会員でこれらの列を使うか |
|---|---|
| 公開ポータルの本人確認（BR-19） | **使わない**。`勤務先名` ＋（事業所番号 or 勤務先電話） |
| 同一人物判定の索引（BR-08） | **使わない**。`memberType !== 'BUSINESS'` で明示的に除外 |
| 保存時の検証 | **使わない**。事業所会員は姓・名・CM 番号の必須を免除 |
| 宛名（BR-04） | **使わない**。宛名は `勤務先名` |

**実質的な読み手が 1 つも無い。** 一方で同期すれば、代表者が交代するたび会員行を書き換える
義務が生じ、正本が 2 つになる（BR-02 は `T_事業所職員` を正本と定めている）。

> 当初「同期すると、職員追加時に同じ CM 番号の事業所会員レコード自体が職員へ変換される
> のではないか」と懸念したが、**索引を作る側に既にガードがあり起きない**。
> 推測のまま報告せず確認した。

operator 判断で**実装を正とし、仕様書（RD 1.9）を実態に合わせた**。
