## 1. 検査のやり方

`scripts/test-validation-matrix.mts` は**実装を文字列照合しない**。
gas-src から `validateMemberPayload_` などの本体を取り出して Node 上で実行し、
入力 → 受理/拒否 の表を回す。文字列照合は「書いてある」ことしか言えず、
「効いている」ことは言えないため。

未達は skip しない。**「仕様では拒否のはずだが実装は受理する」ことを assert で固定**し、
直ったらテストが落ちて記録を外すよう促す。未達を放置せず、かつ見失わないため。

```
npm run test:validation-matrix   # 51 件
npm run test:db-relations        #  7 件
```
どちらも `prerelease` に組み込んだ。

## 2. 仕様未達 6 件

### ★1. 電話番号・郵便番号・メールアドレスの書式を、サーバが検証していない（BR-15 / BR-18）

BR-15 は「電話番号系は入力がある場合のみ半角数字とハイフンを許可する」と書き、
BR-18 は「画面側の検証は入力の手助けであり、**最終判定はサーバーで行う**」と書いている。

実際には `validateMemberPayload_` に書式検証が一切無い。あるのは**必須かどうか**だけ。
書式は画面の `PHONE_PATTERN` / `POSTAL_CODE_PATTERN` / `EMAIL_PATTERN` だけが見ている。

検査表で実際に通ることを確認した値:

| 項目 | 値 | 結果 |
|---|---|---|
| 携帯電話番号 | `でんわばんごう` | **受理** |
| 勤務先電話番号 | `!!!!!!` | **受理** |
| 自宅郵便番号 | `あいうえお` | **受理** |
| メールアドレス | `not-an-email` | **受理** |

公開ポータルの変更申請は `submitPublicChangeRequest_` で allowlist と `trim` を通るだけなので、
**画面を経由せず API を叩けば、これらがそのまま `T_会員` に入る。**
郵便が出せない住所・届かないメールアドレスが、承認を経て正規のデータになる。

### ★2. 事業所番号の桁数を、保存時に検証していない（BR-16）

BR-16 は「事業所番号は公開申込では半角英数字 10 文字」。
検証しているのは公開申込フォームだけで、`validateMemberPayload_` は事業所番号を見ていない。
管理画面からの保存・変更申請の承認では、`ABC` のような値が通る。

### ★3. ADMIN が自分自身のロールを変更できる（BR-06）

BR-06:「`ADMIN` は…**自分自身のロールも変更できない**」

`validateBusinessStaffRoleTransition_` が見ているのは代表者がらみの遷移だけで、
自分自身かどうかは見ていない。実行して確認した結果:

| 操作（実行者＝ADMIN） | 仕様 | 実装 |
|---|---|---|
| 他の職員を ADMIN ⇄ STAFF | 可 | 可 ✅ |
| 代表者のロールを変更 | 不可 | 不可 ✅ |
| 誰かを代表者にする | 不可 | 不可 ✅ |
| **自分を STAFF にする** | **不可** | **可 ★** |

**権限昇格ではない**（自己降格のみ。代表者化は拒否される）。影響は、管理者が自分を
降格させて事業所に ADMIN が居なくなりうること。

### ★4. 事業所の退会申請「代表者のみ」が素通りしうる（BR-11）

BR-11:「事業所会員の退会申請は代表者のみ。管理者・一般職員は申請できない」

実装はこの形をしている。

```js
if (memberType === 'BUSINESS') {
  var staffId = String(authRow[authCols['職員ID']] || '');
  if (staffId) {
    if (staffSheet) {
      if (staffFound) {
        if (staffRole !== 'REPRESENTATIVE') throw ...
```

**条件が 1 つでも外れると、何も検証せず退会申請が通る。** 認証アカウントに職員IDが
無い事業所会員、または職員行が見つからない場合がそれにあたる。
ガードは満たせないときに通すのではなく、止めるべき（fail-closed）。

なお退会申請そのものはパスワード再入力を必須にしており（BR-11）、ここは効いている。

### ★5. 経費請求の添付が、実在するファイルか確認されていない（BR-09）

BR-09:「経費請求は添付ファイルを必須とし、**保存時にサーバー側でも添付の有無を検証する**」

`uploadClaimAttachment_` は MIME（PDF/JPEG/PNG）とサイズ（10MB）を検証していて、ここは正しい。
しかし `saveClaim_` は `payload.attachmentsJson` の**件数しか見ていない**。
中身がアップロード済みのファイルに対応しているかは確認しない。
画面を通さず `attachmentsJson: [{name:'領収書'}]` を送れば「添付あり」として受理される。

管理者が承認前に内容を確認する運用（BR-09 の最後の行）なので実害は止まるが、
サーバー側の検証としては成立していない。

### ★6. マスタを参照しているのに、入力規則もコード検証も無い列が 5 つ（BR-18）

この DB は Spreadsheet なので外部キー制約が張れない。代わりに `入力規則定義` が
シートの入力規則（プルダウン）を張り、**これが DB 側で効く唯一の制約**。
次の 5 つはそこから漏れていて、かつコードでも検証していない。

| 列 | 参照先 |
|---|---|
| `T_研修申込.出欠状態コード` | `M_出欠状態` |
| `T_請求.役職コード` | `M_役職マスタ` |
| `T_支払い明細.役職コード` | `M_役職マスタ` |
| `M_役職マスタ.組織コード` | `M_組織マスタ` |
| `M_業務分類.組織コード` | `M_組織マスタ` |

とくに `T_研修申込.出欠状態コード` は `saveAttendance_` が
`data[r][cols['出欠状態コード']] = payload.status;` と**無検証でセルへ書いている**。
`T_請求.役職コード` も `saveClaim_` が payload の値をそのまま書く。
どちらも管理者・役員に限定された経路なので外部からは叩けない。

> `T_規程.対象会員種別` も入力規則が無いが、選択肢が `M_会員種別` + `ALL` で
> マスタそのままでは表せず、`REGULATION_TARGETS` で検証している。未達ではない。

### 3.2 構造上の限界 — ID 参照 24 件は DB では守られない

Spreadsheet の入力規則はマスタの選択肢にしか使えない。
**「`会員ID` が `T_会員` に実在すること」は誰も保証しない。**
該当する参照は 24 件。

```
T_事業所職員.会員ID → T_会員                 T_研修申込.会員ID → T_会員
T_認証アカウント.会員ID → T_会員             T_研修申込.職員ID → T_事業所職員
T_認証アカウント.職員ID → T_事業所職員       T_研修申込.外部申込者ID → T_外部申込者
T_年会費納入履歴.会員ID → T_会員             T_研修申込.研修ID → T_研修
T_年会費更新履歴.会員ID → T_会員             T_メール送信明細.ログID → T_メール送信ログ
T_年会費更新履歴.年会費履歴ID → T_年会費納入履歴  T_メール送信明細.研修ID → T_研修
T_役員.会員ID / 職員ID                       T_ログイン履歴.認証ID → T_認証アカウント
T_振込口座.会員ID / 職員ID                   T_管理者Googleホワイトリスト.紐付け会員ID / 紐付け認証ID
```

これは欠陥ではなく、DB の選択（Spreadsheet）から来る制約。
`test:db-relations` が件数を固定しており、**守られない参照を増やしたら落ちる**。

### 3.3 まだできていないこと — 実データの孤児行検査

AI 側ではパスワードを入力できないため到達できなかった。`clasp run` も従来どおり権限で通らない。

## 4. 対応の優先順（提案）

| | 内容 | 理由 |
|---|---|---|
| 1 | ★1 書式検証をサーバへ | 画面を経由しない経路が実在し、DB に不正値が入る。影響が最も広い |
| 2 | ★4 退会ガードを fail-closed へ | 条件分岐を閉じるだけで直る。仕様の権限制約が外れうる |
| 3 | ★6 入力規則 5 件の追加 ＋ 出欠状態コードの検証 | DB 側の制約を増やせる |
| 4 | ★2 事業所番号を保存時検証へ | ★1 と同じ場所で直せる |
| 5 | ★3 自己ロール変更の禁止 | 昇格ではないため急がない |
| 6 | ★5 添付の実在突き合わせ | 承認前の目視で止まるため急がない |

★1 と ★2 は同じ関数（`validateMemberPayload_`）で、書式の正本を
`src/shared/validators.ts` と二重に持たない形にする必要がある（DRY）。
GAS へ regex を注入すると build pruner の罠を踏むため（`feedback_build_pruner_regex_action_traps`）、
`String.indexOf` 系か、文字種を数える実装で揃える。
