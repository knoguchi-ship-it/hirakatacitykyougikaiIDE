# 0. 正本マトリクス（最初に合意する）

**このテンプレートで最も重要な表。** 主題ごとに正本を 1 つ決め、他の文書は参照だけを書く。
着手前にこの表を提示し、案件に合わせて調整したうえで合意を取る。

| 主題 | 正本 | 他文書での扱い |
|---|---|---|
| 事業上の目的・作業範囲・**非機能の目標値** | **SOW** | 参照のみ |
| 用語の定義 | **SOW（用語集）** | 参照のみ |
| 業務ルール・ユースケース・権限の**意味** | **RD** | 参照のみ |
| 技術構成・実装方式・**性能上の対策**・移行 | **TRD** | 参照のみ |
| 画面・遷移・表示条件・通知と文言の規約 | **UI/UX** | 参照のみ |
| データの規約（キー・型の方針・削除・IF 契約） | **データIF** | 参照のみ |
| **列定義・入力規則の値・API の型・定数** | **コード / 自動生成物** | **取得元を書く。値を書き写さない** |

## 0.1 コードが正本になる場合の書き方

次に当てはまるものは、文書に値を書かない。

- 型検査・単体テスト・生成物のドリフト検査など、**機械が守っている定義**
- スキーマから自動生成される ER 図・テーブル設計書
- 1 箇所に集約された定数・列挙・検証パターン

代わりに次の 3 つを書く。

1. **取得元**（ファイル名・生成コマンド・閲覧できる HTML など）
2. **変更したときの手順**（何を直し、何を再生成し、どのゲートを通すか）
3. **機械が見ていない例外**（運用でしか担保できない部分）

## 0.2 省略のしかた

テンプレートの節を置かない場合は、その文書内に 1 行で書く。

> 本書に「◯◯」の節は置かない。正本は △△ であり、変更手順は □□ に従う。

## 1.2 ID の付け方

| 接頭辞 | 対象 | 置く文書 |
|---|---|---|
| `SC-xx` | 作業範囲の項目 | SOW |
| `NF-xx` | 非機能要件 | SOW |
| `TM-xx` | 用語 | SOW |
| `BR-xx` | 業務ルール | RD |
| `UC-xxx` | ユースケース | RD |
| `TR-xx` | 技術要件・実装方式 | TRD |
| `MG-xx` | 移行・並走の手順 | TRD |
| `SCR-xx` | 画面 | UI/UX |
| `DI-xx` | データ規約・IF 契約 | データIF |
| `Q-xx` | 未確定事項 | 各文書（末尾に集約） |

**ID は再利用しない。** 廃止しても欠番のまま残し、改訂履歴に廃止を書く。

## 1.3 検証方法の列

要件を並べる表には必ず「検証方法」の列を置く。**空欄を認めない。**

| 書ける値 | 例 |
|---|---|
| 自動テスト | `npm run test:xxx` / `dryRunXxx_LOG` |
| 機械検査 | リリース前ゲート・境界検査 |
| 手動確認 | 「operator が実機で◯◯を確認」 |
| **未検証** | **「未検証。◯◯のため機械化できていない」と理由まで書く** |

# 4. Step 9: 整合確認

すべての文書を出し終えたら、次を確認して結果を表で出す。

| # | 確認 | 落ちたときの直し方 |

| 1 | 同じ内容が 2 文書に書かれていないか | 正本を 1 つ決め、他方を参照に置換 |

| 7 | 未確定事項が 1 箇所に集約され、判断者が書かれているか | 各文書の末尾へ集約 |
