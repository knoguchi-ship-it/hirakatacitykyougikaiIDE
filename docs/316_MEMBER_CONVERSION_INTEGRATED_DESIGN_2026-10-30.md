# 316 会員種別移行の全体設計（2026-10-30）

## 1. 目的と状態

個人・賛助会員と事業所職員の双方向の移行で、会員、職員、認証と研修申込等の人物参照を整合させる。既存機能の検証で判明した S46 と、役員等の別人参照まで更新する問題を扱い、研修の新機能からも再利用できる境界を作る。

**本書は移行全体の統合設計案。** 後勝ちと異常時の既存 Chat 通知は operator 指示。研修申込・認証アカウントの表と必須列の事前検知・共通通知はローカル実装済み。具体的な一括更新方式は実行環境・データ型・失敗時の検証後に採否を確定する。現時点で本番に適用されていない。過去の本番データの誤更新の有無は未確認。別人の人物参照を選ぶ問題はローカル修正済みで、移行全体は未完成。経緯と模擬確認は [docs/307](307_REMAINING_FINDINGS_INVENTORY_2026-10-14.md) S46 を参照。

## 2. 固定する方針

1. **同時編集は後勝ち。** 今回、別プロジェクトをまたぐ排他機構は追加しない。既存の管理 project のスクリプトロックの扱いは別途確認し、暗黙に削除しない。公開・会員・管理 project 間やシート直接編集は同じロックで保護されない。
2. **一つの移行は一つの業務処理。** 入力不備・参照不整合があれば、可能な限り最初の書込み前に中止し、正常完了として扱わない。途中失敗で複数表が食い違うことと、後勝ちは別の問題である。
3. **データの異常時だけ、既存の会員手続き「要確認」通知を使う。** 正常処理や通常の後勝ちでは異常通知しない。既存の全体・要確認設定に従い、設定や Webhook を新たに設けない。
4. **本人の正本を使う。** 研修申込は既存の会員ID・職員IDの条件、役員関連は `officerPersonRef_` / `rowBelongsToOfficerPerson_` を使う。事業所の会員IDと職員IDを単純な OR で照合しない。
5. **実データ、認証情報を模擬テストやログに複製しない。** 本番への書込み・外部送信・テストデータ作成と削除は案件の既存承認・運用手順に従う。

## 3. 対象と責務

| 部品 | 入力・責務 | 結果 |
|---|---|---|
| 移行受付 | 管理者権限、方向、元・先のID、代表者等を検証 | 許可された移行要求 |
| 読取・検証 | 必要な表・列・対象を読み、本人、状態、重複、上限、代表者、参照の整合を確認 | 正常な読み取り結果、または理由付きの中止 |
| 移行計画 | IDの生成・再利用を確定し、更新対象と更新列、操作ID、記録を組み立てる | 変更計画。DB書込み・外部通知なし |
| 実行 | 計画の対象データを一つの書込み単位にする方式を実行 | 適用済み・未適用・結果不明 |
| 結果・異常通知 | 操作画面へ結果を返す。データ異常のときだけ既存 Chat の `ANOMALY` を呼ぶ | 操作者が次の行動を判断できる表示 |

本体の更新範囲は方向・既存状態により異なる。会員、事業所職員、認証アカウント、必要な管理者紐付け、研修申込、役員・振込口座・請求・支払い、人物統合ログを対象として棚卸しする。代表者変更・最後の代表者の移行による事業所退会も計画に含める。個人同士の統合では年会費履歴も対象であり、転籍と同じ参照ヘルパーを共有する箇所は回帰範囲に含める。通知・キャッシュ消去は外部処理として更新後に扱う。

## 4. 正常時の流れ

1. 既存の認証・認可境界を通り、移行要求をサーバー側で検証する。
2. 読取専用で対象表と必要列、移行元と移行先の状態、既存行の再利用候補、関連する参照を調べる。無い表・列と「存在するが該当行が0件」は区別する。ID が空、対象が複数、状態が矛盾など確認不能な場合は移行しない。
3. 職員・会員・認証の対応関係と関連参照、代表者・事業所状態、変更後の本人の参照を計画する。更新対象は列単位とし、関係しない人物や列を書き戻さない。ID生成・再利用候補が一意であることを確かめる。
4. 計画に含む全 DB 更新と、結果確認に使う操作IDの完了記録を同一単位で書く。`spreadsheets.batchUpdate` が候補。後勝ちは同じ列への後からの適用を採用し、読取後の同時変更や直接シート編集との競合は本方式だけでは防げない。
5. DB更新の成功が確認できてから、キャッシュを無効化し、画面へ成功を返す。正常時の異常通知は出さない。キャッシュ等の失敗を DB 未更新と誤認させない。

### 一括更新の採用条件

Google の [Sheets API 仕様](https://developers.google.com/workspace/sheets/api/reference/rest/v4/spreadsheets/batchUpdate) は、単一スプレッドシート内の要求をまとめて原子的に適用するとしている。ただし他の同時編集の影響は保証しない。実装前に、対象表がすべて同じファイルにあること、API利用と権限、列単位更新、行追加、日付・数式・ゼロ始まりの値、書式維持、操作記録の同時追加、サイズ・実行時間を実環境に近い条件で確認する。通常 API の上限・推奨サイズは [Google の制限](https://developers.google.com/workspace/sheets/api/limits) を参照。条件を満たさなければ、処理記録と復旧方式を再設計し、分割送信を原子的と見なさない。

## 5. 異常と通知

| 種類 | 例 | DBと画面 | Chat |
|---|---|---|---|
| データ異常 | 必要表・列なし、同一人物が特定不能、必須参照の欠落・矛盾 | 書込み前に停止し、何を確認するか表示 | 既存の要確認通知へ、事象種別と必要最小限の対象識別子を送る |
| 通常の入力不備 | 未選択、必要な入力の不足 | 画面に入力方法を表示 | 異常通知しない |
| 実行・通信障害 | API拒否、通信断、応答喪失 | 結果を未適用／不明として示し、再実行前の確認を案内 | データ異常として一律に通知しない。既存の障害運用は維持 |
| 通知無効・送信失敗 | 要確認通知が停止、設定不足、送信失敗 | データ異常の中止・画面表示を維持し、安全な内部記録で追跡 | 送信成功とは扱わない |

データ異常のコード・判定条件は実装時に許可リストで定義し、表示・通知・テストが同じ定義を使う。手動入力の誤りをすべて異常扱いせず、参照先の不整合等を区別する。送信対象やテンプレートは既存 `notifyMembershipChatSafely_` と設定の正本に従う。通知にはパスワード、認証情報、生の例外、メールアドレス等を載せない。通知を再送する場合も重複・失敗を見える形で扱う。

### Chat 送信の共通化（DRY）

- Chat の送信出口は既存の `notifyMembershipChatSafely_` を正本とし、移行専用の HTTP 送信・Webhook の読取・別の設定やテンプレート描画を作らない。既存の会員手続き通知は `REQUEST` / `FINAL` / `ANOMALY` の種別で同じ関数を使い、設定・本文と差し込み値を切り替えている。会員情報の補完が必要なら既存 `notifyMembershipChatForMember_` が共通出口に委譲する。
- 移行では `ANOMALY` の既存本文設定と差し込みタグを使用し、検証部品が返す**異常コードから固定の安全な説明文を一箇所で選ぶ**。例えば表・列の不足、本人の特定不能、関連IDの矛盾をそれぞれ区別する。実際のコードと文言は移行の検証条件と合わせて定義し、画面・通知の双方から参照する。
- 未知の異常コードは正常扱いや任意の例外文字列の送信にせず、一般的な要確認として中止し、具体的な内部情報を外へ出さない。通知本文・宛先・設定の正本を複製せず、送信有効／無効・送信失敗・正常時に通知しないことを共通出口を差し替えた実行テストで確認する。
- 既存の通常通知・定期ジョブ・メール送信障害での設定、差し込み、送信結果の扱いを維持する。

**表・列の棚卸し（2026-10-31）:** 移行が書く表は T_会員・T_事業所職員・T_認証アカウント・T_管理者Googleホワイトリスト（紐付け会員ID）・T_研修申込（会員ID・職員ID・申込者ID）・T_役員・T_振込口座・T_請求・T_支払い・T_人物統合ログ。すべて DB スプレッドシートにあり、ログ用スプレッドシートの表を含まない。書かない表と理由: T_年会費納入履歴・T_年会費更新履歴（会員→会員の統合のときだけ）、T_ログイン履歴（認証IDは変わらない）、T_削除ログ（過去の記録）、T_支払い明細（支払いIDで辿る）。operator 決定（2026-10-31）:
- **A 構造確認を全表へ（実装済み・ローカル）。** 書く表と無条件に使う列は `MEMBER_CONVERSION_REQUIRED_COLUMNS_` の一か所で定め、`inspectMemberConversionData_` が書込み前にすべて確かめる。以前は 2 表だけで、役員まわり 4 表とホワイトリストは表・列が無いと 0 件として素通りした。T_人物統合ログは無ければ作るので含めない。個人会員の新規作成は `appendRow`（テーブル定義の列順）から `appendRowsByHeaders_`（シートの見出し順・番号の文字列書式）に変えた。
- **B 照合会員ID・照合職員IDは付け替えない。** 外部申込を会員と突き合わせた申込時点の記録として扱う。移行後に削除済みの職員IDを指していても誤りではない。
- **C 処理待ちの変更申請があれば書き込む前に止める（実装済み・ローカル）。** 申請は移行前の会員ID・職員IDを指すため、移行後に承認すると別の人や退会済みの行に効く。DB に書いた後の巻き戻しは、途中失敗や後から入った変更を消すおそれがあるため採らず、読み取りの段階で止める（結果は書き込みゼロ）。流れ: ①画面に申請IDと「承認または却下してから、もう一度移行」を表示 ②管理者が申請を処理 ③移行をやり直す ④移行後も変更が必要なら本人が申請し直す。本人の申請とは、(a) 会員IDが一致する個人・賛助会員の申請、(b) 事業所（職員→個人では元の事業所、個人→職員では転籍先）の申請のうち、この人を職員の追加・情報変更・除籍の対象に含むもの（情報変更は職員ID、追加・除籍は介護支援専門員番号で照合）。処理待ちの申請は通常の業務状態なので Chat 通知しない。申請内容の JSON が読めない申請は本人のものか確かめられないため、止めたうえで既存の `ANOMALY` に通知する。`findConversionPendingChangeRequests_` / `assertNoConversionPendingChangeRequests_`。T_変更申請 は読むだけだが構造確認の一覧に含める。

**残る穴（次の段階）:** 書き込む前の確認で防げるのは「読めば分かる問題」だけ。確認を通過した後の書込み途中の失敗（API エラー・通信断・実行時間切れ）では、1 行ずつの書込みのため表どうしが食い違いうる。§4 の一括更新と §6 の操作IDで扱う（operator 了承 2026-10-31）。

**実装状況（ローカル・未リリース）:** `inspectMemberConversionData_` は、上記の書込み対象の全表と移行に必要な列を調べ、書込み前に不足を検知する。移行の受付は既存 `notifyMembershipChatSafely_` の `ANOMALY` へ、固定の表・列名だけを含む説明を渡し、移行を止める。正常時・無効な方向では通知しない。通知の停止や送信失敗でも移行は止める。`test:officer-person`（25 件）で実際の部品・受付を実行し、正常・表なし・列なし・通知停止／失敗、全表の列がテーブル定義に存在すること、書く表がすべて一覧にあること、処理待ち申請 5 パターンで DB 不変・通知なし、読めない申請で停止と通知を検証した。他の表・行や本人の参照整合、書込み途中の失敗・復旧、操作結果不明の検証はまだ対象外。本番の通知設定・送信は未確認。

**ブラウザ確認（2026-10-30）:** 実際の会員詳細画面と API クライアント、抽出した移行受付・異常検知関数を使い、DB・通知・正常時の移行本体は模擬した。異常時は移行本体 0 回・通知出口 1 回、正常時は移行本体 1 回・異常通知 0 回。エラーがモーダルの背後に隠れることを検出し、3 種の転籍モーダル内に共通のエラー表示を移した。個人→事業所の模擬異常で 360px・1920px にて表示と横あふれなしを確認。他の 2 モーダルの実ブラウザ確認、実 GAS・実 DB・実 Chat を通る E2E は未実施。

## 6. 応答不明と復旧

- 各移行に操作IDを付け、完了記録を DB 更新と同じ単位に入れる設計とする。画面は応答喪失時に成功・失敗を推測しない。
- 同じ操作IDの記録が確認できれば結果を照会する。記録が見つからないだけでは、処理が進行中または応答未確定の可能性があるため即座に未実行と断定しない。
- 不明の場合は自動再送せず、操作者に確認・復旧の手順を示す。二重実行が同時到着した場合の完全な重複防止は、新たな排他・条件付き書込みなしでは保証しない。この制約を利用者と運用へ明示し、同時実行の扱いを実装前に確定する。
- 処理記録の保存先、既存の人物統合ログを再利用できるか、記録の保持期間、結果不明時の確認手順は実機検証で具体化する。補償処理を採用するなら途中停止や補償自体の失敗まで扱い、無条件の巻き戻しで後からの変更を消さない。

## 7. 検証と完了条件

通常の開発では変更部品とその利用先だけを対象にする。ローカルでは実装関数を実行し、①双方向の新規・再利用 ②本人以外に触れない ③空の表と欠落表・欠落列 ④認証・代表者・関連IDの不整合 ⑤上限 ⑥最初・途中・完了後の失敗 ⑦通知の有効・停止・失敗 ⑧応答喪失と結果照会 ⑨後勝ちの想定範囲を確認する。構造の照合は配線の確認に限る。

生成物の変更があれば 3 split の同期・参照・境界と関連テストを実行。Sheets API 方式は本番データを使わない隔離環境で失敗注入・データ型・応答不明を確認する。必要な本番 DB 確認、テストデータ作成・削除は operator の承認と `/dbops` の手順に従う。全体の `prerelease` は push / release 前に実施する。

完了の判定には、対象表・列の全棚卸し、方式の実行確認、通知条件の具体化、操作IDと再実行の扱い、画面メッセージ、既存データの読み取り診断方法が必要。S39 の初期化・退会ジョブは別機能として残す。
