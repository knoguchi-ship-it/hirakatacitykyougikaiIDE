# 317 会員・職員移行のテスト計画（一括更新方式と E2E）

> 作成 2026-10-31。設計の正本は [docs/316](316_MEMBER_CONVERSION_INTEGRATED_DESIGN_2026-10-30.md)。本書は検証の手順・合格条件・承認点だけを持つ。
> **状態: P は実施済み（2026-10-31・§9.1。P5 の日付以外合格）。I・E・S は未実施（未検証）。** 実施したら §9 に結果を追記する。

## 1. 目的

docs/316 の残る穴「確認を通過した後の書込み途中の失敗で、表どうしが食い違う」を塞ぐ方式（Sheets API `spreadsheets.batchUpdate` による一括更新＋操作ID）を、

1. 採用してよいかを実環境で確かめ（P）、
2. 実装を部品単位で検証し（I）、
3. 実 GAS・実スプレッドシートで移行全体を通し（E）、
4. 最後に本番画面から双方向の移行を確かめる（S）。

模擬 DB の成功を実 GAS・実 DB・実 Chat の成功と混同しない（HANDOVER 再開プラン 2）。各層の合格は、その層で確かめた範囲だけを意味する。

## 2. テストの層

| 層 | どこで | 何を確かめる | 本番への影響 |
|---|---|---|---|
| **L1 ローカル** | `npm run test:officer-person` ほか（Node・模擬シート／模擬 API） | 計画の組み立て、要求の形、異常の分類、失敗注入 | なし |
| **L2 隔離 E2E** | 実 Apps Script（admin split の保守ツール）＋**一時スプレッドシート** | 実 API の原子性・データ型・書式・時間、移行全体 | 本番 DB に書かない。一時ファイルを作って消す |
| **L3 本番画面 E2E** | Playwright（`/prodcheck`）で管理画面を操作、本番 DB | 画面〜API〜DB の配線、表示、後片付け | ★テストデータを作り、物理削除する |

### 2.1 隔離の仕組み（L2）

- 移行関数は `ss` を引数で受け取り、Chat 設定・マスタ・職員数上限もその `ss` から読む（2026-10-31 確認）。例外は入口の `convertMemberType_` だけで、`getOrCreateDatabase_()` で本番 DB を開く。
  → **入口を「DB を決める部分」と「渡された `ss` で移行する部分」に分ける**（I0）。保守ツールは後者に一時スプレッドシートを渡す。
- 一時スプレッドシートは実行のたびに `テーブル定義` の見出しで作り、合成データ（氏名の先頭に★、メールは `@example.invalid`）だけを入れる。**本番の行を複製しない**（docs/316 §2-5）。
- 一時スプレッドシートには Chat の設定が無い。そのため異常通知は「設定なし＝送らない」で終わり、実送信は起きない。送る経路の確認は L3 で、既存の宛先設定に従って別に扱う。
- 既知の副作用: キャッシュの消去（`clearAllDataCache_` 等）は本番のキャッシュに効く。性能に一時的に響くだけでデータは変わらない。マスタの読込みはスクリプトキャッシュを共有しうる（読むだけ）。
- 終わったら一時スプレッドシートはゴミ箱へ移す。失敗で残った場合は、ファイル名の接頭辞 `★E2E移行検証_` で探して手で消す。

## 3. P: 一括更新方式の実地確認（L2・採否の判定）

保守ツール `probeSheetsBatchUpdate_LOG`（仮称・MASTER 限定・admin split のみ・`/gas-admin-tool` の手順で登録）が、一時スプレッドシートに対して次を実行し、結果を記録して返す。

| ID | 確かめること | 合格条件 |
|---|---|---|
| P1 | 正常な複数表・複数行の更新を 1 回の `batchUpdate` で送る | 全セルが期待値。応答の件数が要求と一致 |
| P2 | **原子性**: 正常な要求の後ろに、必ず失敗する要求（存在しない sheetId 等）を混ぜる | API がエラーを返し、**前半の正常な要求も 1 セルも反映されない** |
| P3 | 行の追加（新規会員・職員・ログ）と既存行の更新を同じ要求に入れる | 追加行がシートの見出し順で入り、既存行の対象列だけが変わる |
| P4 | **列単位更新**: 対象列だけを書き、隣の列は書かない | 対象外の列（同じ行の他列・同僚の行）は全列不変 |
| P5 | データ型: 先頭 0 の番号・電話、8 桁の介護支援専門員番号、日付文字列 `yyyy-MM-dd`、ISO 日時、真偽値、空文字 | 読み戻した値が `SpreadsheetApp` の既存書込みと同じ型・表記。数値化・日付化・0 落ちが起きない |
| P6 | 書式・入力規則: 書式なしテキスト列（`TEXT_FORMAT_COLUMNS_`）、プルダウンの入力規則 | 既存の書式・入力規則が残る。追加行にも書式なしテキストが効く |
| P7 | 数式セル・保護範囲が近くにある場合 | 数式が上書きされない（対象列に数式が無いことも確認） |
| P8 | 規模と時間: 本番相当の行数（`describeDatabaseState_LOG` の件数を目安）で、1 回の移行に要る要求の大きさと所要時間 | 要求サイズが Google の推奨範囲内、所要時間が GAS の実行上限に十分余裕 |
| P9 | 操作記録の同時追加: 完了記録（操作ID）の行を本体の更新と同じ要求に入れる | 本体が反映されたときだけ記録がある。P2 の失敗時は記録も無い |
| P10 | 権限: admin の実行ユーザー・既存スコープ（`spreadsheets`・`script.external_request`）で呼べる | スコープ追加・再承認なしで成功 |

**採否の判定**: P1〜P10 がすべて合格なら一括更新を採用する。P2 か P9 が不合格なら、この方式で「全部か無しか」は得られない。その場合は docs/316 §4 の条件どおり処理記録と復旧方式を設計し直し、分割送信を原子的と見なさない。結果は operator に報告して方針を決める。

## 4. I: 実装の部品検証（L1）

docs/316 §3 の部品ごとに、ローカルで実装関数そのものを実行する。Sheets API は要求を記録して模擬応答・失敗を返す差し替えで置き換える。

| ID | 対象 | 確かめること（docs/316 §7 の番号） |
|---|---|---|
| I0 | 入口の分離 | DB を決める部分と移行部分を分け、移行部分は渡された `ss` だけを使う（本番 DB を開かない）ことを、ソースと実行の両方で確かめる |
| I1 | 読取・検証 | ③空の表と欠落表・欠落列（済）、④認証・代表者・関連IDの不整合、⑤上限、処理待ち申請（済） |
| I2 | 移行計画 | ①双方向の新規・再利用で、更新対象の行・列・新しいID・操作ID が一意に決まる。②本人以外の行・列が計画に入らない。計画を作る段階で書き込みが 0 回 |
| I3 | 要求の組み立て | 計画 → `batchUpdate` 要求の変換。列単位で、行追加は見出し順。型（P5 の結果に合わせる） |
| I4 | 実行と結果 | ⑥最初・途中・完了後の失敗の注入で、「適用済み／未適用／不明」を正しく返す。未適用のとき画面は再実行を案内し、不明のとき自動再送しない |
| I5 | 結果照会 | ⑧応答喪失（API は成功したが応答を受け取れない）で、操作ID の記録から結果を照会できる。記録が無いだけで未実行と断定しない |
| I6 | 通知 | ⑦データ異常のときだけ `ANOMALY`。有効・停止・送信失敗でも移行の判定は変わらない（済の範囲を維持） |
| I7 | 後勝ち | ⑨同じ人への 2 回目の移行、計画後に他の列が変わった場合の振る舞いを、想定どおり（同じ列は後勝ち・他の列は触らない）と記録する |
| I8 | 回帰 | 既存の `test:officer-person` の 2 方向（本人の参照が移る・他人の行の全列不変）が新方式でも通る |

## 5. E: 移行全体の隔離 E2E（L2）

保守ツール `e2eMemberConversionIsolated_LOG`（仮称・MASTER 限定・admin split のみ）が、シナリオごとに一時スプレッドシートを作り、合成データを入れ、**本物の移行関数**を実行して、全表を読み戻して判定する。

| ID | シナリオ | 合格条件 |
|---|---|---|
| E1 | 個人→職員（新規の職員行） | 会員 TRANSFERRED、職員 ENROLLED、認証・研修申込・役員まわり 4 表・ホワイトリストが新しい参照へ、人物統合ログ 1 行。他人の行は全列不変 |
| E2 | 個人→職員（同じ事業所の LEFT 行を再活性化） | 既存の職員IDを再利用し、新しい行を作らない |
| E3 | 職員→個人（新規の個人会員行） | 新会員が見出し順で追加され、介護支援専門員番号の先頭 0 が保たれる |
| E4 | 職員→個人（WITHDRAWN の個人行を再活性化） | 既存の会員IDを再利用 |
| E5 | 職員→個人・代表者で後任あり | 後任が REPRESENTATIVE、本人は LEFT |
| E6 | 職員→個人・最後の 1 名の代表者 | 事業所が WITHDRAWN（退会日つき） |
| E7 | 往復（個人→職員→個人） | 行が増えず、同じ会員ID・職員IDに戻る。研修申込・役員の参照が元に戻る |
| E8 | 停止: 処理待ちの変更申請、表・列の欠落、CM 番号重複、上限超過、後任未指定 | 例外のメッセージが画面用の文言。**全表が実行前と完全に一致** |
| E9 | 失敗注入: 一括更新の要求に失敗する要求を混ぜる（P2 と同じ仕組み） | 全表が実行前と一致し、結果「未適用」 |
| E10 | 応答喪失の模擬: 適用後に応答を捨てる | 結果照会で「適用済み」と分かる。自動再送しない |
| E11 | 規模: 本番相当の行数で E1・E3 | 所要時間を記録し、P8 と矛盾しない |

各シナリオは前後の全表のスナップショットを比べ、変わってよいセルの一覧（期待差分）と完全に一致することを合格とする。「エラーが出なかった」だけでは合格にしない（`feedback_dont_overtrust_tests`）。

## 9. 実施記録

### 9.1 P 一括更新方式の実地確認（2026-10-31・admin split HEAD `9bf1062a`・`clasp run`）

実行経路は Skill `/prodcheck` §1.5（同日確立）。一時スプレッドシートは実行後ゴミ箱へ移動済み（`trashed: true`）。所要 22 秒。
本番の規模（`describeDatabaseState_LOG`）は T_会員 241 行・T_事業所職員 190 行・T_認証アカウント 358 行。P8 は 1 表 2000 行で測った。

| ID | 結果 | 実測 |
|---|---|---|
| P10 権限 | 合格 | 200。スコープ追加・再承認なし |
| P1 複数表の更新 | 合格 | 5 セル更新＋操作記録 1 行・応答 6 件・315ms |
| P2 **原子性** | 合格 | 存在しないシートへの要求を混ぜると 400 `INVALID_ARGUMENT`、**変化 0 セル・追加 0 行** |
| P9 操作記録 | 合格 | 成功時だけ 1 行、失敗時 0 行 |
| P3 行追加＋更新 | 合格 | 同じ表へ 2 行を要求順に追加し、更新は 1 セルだけ |
| P4 列単位 | 合格 | 対象外のセルの変化 0 |
| P5 型 | **不合格（想定内）** | 番号（書式なしテキスト）・ISO 日時・真偽値・空は同じ。**`yyyy-MM-dd` の日付だけ、既存の書き方では日付型、一括更新（`stringValue`）では文字列** |
| P6 入力規則・書式 | 合格 | 入力規則は残り、追加行の番号列はテキスト書式で先頭 0 も残る |
| P7 数式 | 合格 | 同じ行の数式は残る |
| P8 規模 | 合格 | 43 要求・11KB・370ms。2 表 4000 行の読取 634ms |

**観察 P0（実装の前提）**: Sheets API で書いた直後に、**同じ実行の SpreadsheetApp で読むと古い内容が返る**（`sameObjectSeesWrite: false`・API の読取は新しい内容）。
初回実行（同日・HEAD `fb31f716`）はこれで確認側が誤って NG になった。移行の実装では、

- API で書いた後に、同じ実行で SpreadsheetApp で読んで判定・再計算しない（書いた結果の確認は API から読む）。
- API で書いた後に、同じ実行で SpreadsheetApp で書かない（古い最終行を基準に追加して、API が足した行を上書きしうる）。
- キャッシュの消去・通知など書込み後の処理も、DB を読み直すなら API 経由か、次の実行で行う。

**判定**: 原子性（P2・P9）を含む方式の要件は満たした。一括更新を採用する方向で I（実装）へ進む。P5 の日付は I3 で扱う。
既存データの日付列は日付型（`setValues` が変換）で入っているので、一括更新でも `yyyy-MM-dd` は日付として書く（`numberValue` のシリアル値＋日付書式）案を第一候補とし、読む側の前提を確かめて決める（未決定）。
