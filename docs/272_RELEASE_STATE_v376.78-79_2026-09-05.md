## 1. 直した問題

v376.71 でログイン失敗の**時限ロック**を入れたが、**連続 20 回失敗で到達する恒久ロック**には
解除手段が「資格情報の再発行」しか無かった。

再発行は**パスワードまで変えてしまう**ため、事務局は利用者へ新しいパスワードを伝え直す必要があり、
本人にとっては「ロックされただけなのにパスワードが変わる」という不便が生じていた。

> 正当な利用者は**ログイン成功で失敗回数が 0 に戻る**ため、恒久ロックにはまず到達しない。
> ただしログイン ID が介護支援専門員番号で推測できる以上、**第三者に狙われて到達させられる**可能性は残る。
> その場合の復旧を事務局が自力でできるようにするのが本リリースの目的である。

## 2. 実装（GAS 版・縮小版）

`adminUnlockMemberAccount`（MASTER / ADMIN）を追加した。

| 項目 | 内容 |
|---|---|
| やること | **ロック状態・ログイン失敗回数・ロック解除予定日時**を戻す |
| やらないこと | **パスワードには一切触れない**（ハッシュ・ソルト・更新日時とも変更しない） |
| 排他制御 | `LockService` で直列化 |
| 監査 | `T_監査ログ` に `ACCOUNT_UNLOCK`（実行者・対象認証ID・解除前の状態）。**秘密値は書かない** |
| 拒否条件 | 管理者認証なし／削除済みアカウント／`PASSWORD` 以外の認証方式 |

**判定を 2 箇所に持たないため、ログイン成功時と同じ `clearLoginLockout_` を通している。**
時限解除の仕様（v376.71）が変わったときに、解除処理だけが取り残されることを防ぐ。

### 画面

## 3. なぜ「縮小版」なのか

GAS 側では**ロックを戻すことだけ**を実装した。次のものは入れていない。

| 入れなかったもの | 理由 |
|---|---|
| ロック発生時の管理者への自動通知 | 時間主導トリガーか送信のたびの判定が要る。恒久ロックの発生頻度に対して割に合わない |
| ロック状況の一覧・ダッシュボード | 会員詳細から個別に確認できれば足りる。全件走査は GAS の実行時間に響く |
| 解除の自動化（一定時間で恒久ロックも解除） | 恒久ロックの意味が無くなる。攻撃の継続を許す |

**operator 決定（2026-09-05）**: GAS 側はこの縮小版で運用する。

## 4. GCP 版は別実装として再検討する（明記）

**この機能を GCP へそのまま移さない。移行後に改めて設計する。**

- **理由**: ランニングコストに関わるため（operator 判断・2026-09-05）。
  GCP では認証まわりを Cloud Run `hcmn-member-auth` と Firestore で構成する。
  ロックの監視・通知・自動解除といった「あると便利な機能」を素直に作ると、
  Cloud Scheduler / Cloud Run Job / 通知経路の常時稼働が増え、
  **`docs/271` §7 で維持している「無料枠内に収める」制約**（`docs/250` §15）に影響する。
- **したがって**: GCP 版は「何を作るか」から改めて決める。GAS 版の実装をそのまま移植する前提にしない。
- **移行しても変わらない部分**（そのまま持ち込めるもの）:
  - 「解除はロックだけを戻し、パスワードには触れない」という**振る舞いの契約**
  - ログイン成功時と同じ処理を通す（判定を 2 箇所に持たない）という**設計原則**
  - 解除を監査ログに残す（秘密値は書かない）
- **移行時に決めること**:
  - ロック状態を Firestore のどこに持つか（`authAccounts` のフィールドで足りるか）
  - 恒久ロックの解除を誰が実行できるか（IAP の管理者ロールとの対応）
  - 監視・通知を持つかどうか（**持つならコスト試算とセットで判断する**）

> この節は `AGENTS.md` §4.8.1-5 の「GCP 移植メモ」を兼ねる。
> **未移行 write の増減**: +1（`adminUnlockMemberAccount`）。`docs/250` §6.1 の棚卸しへ追記すること。

## 6. v376.79 — 実機確認の準備中に見つかった不具合（段階的な待機が機能していなかった）

**v376.78 の実機確認をしようとして、恒久ロック（連続 20 回）に到達できないことが分かった。**

### 何が起きていたか

v376.71 の時限ロックは、**待機満了時に失敗回数まで 0 に戻していた**。
一方でロック中の試行は失敗回数を増やさない（早期 return）。この 2 つが噛み合わず、
カウントは `3 → ロック → 待機 → 0` を繰り返し、**4 以上にならなかった**。

実ソースの判定関数を使ったシミュレーション結果:

```
#1 00:00:00 → 失敗(count=1)
#2 00:00:01 → 失敗(count=2)
#3 00:00:02 → 失敗(count=3, ロック 1分)
#4 00:01:03 → 失敗(count=1)   ← 待機満了で 0 に戻され、そこから 1
...
到達した最大の連続失敗回数: 3 ／ 恒久ロックの閾値: 20 → 到達しない
```

| 仕様（`docs/265` §2） | v376.78 までの実際 |
|---|---|
| 3 回目 → 1 分 | 動作 |
| 4 回目 → 5 分 | **到達しない**（死んだ設定）|
| 5 回目 → 15 分 | 到達しない |
| 6 回目以降 → 60 分 | 到達しない |
| 連続 20 回 → 恒久ロック | 到達しない |

つまり **実質「3 回失敗で 1 分待ち」の固定**で、攻撃者は 1 分あたり 3 回の総当たりを
無期限に続けられた。v376.71 が意図した「試行速度を段階的に落とす」効果が出ていなかった。

> v376.71 が解消した本来の問題（5 回失敗で**無期限**ロック＝第三者が他人を締め出せる）は
> 解消されたままで、**以前より危険になっていたわけではない**。

### 修正（operator 決定・案 A）

`releaseLoginLockKeepingFailures_` を追加し、**待機満了はロックと解除予定日時だけを戻す**。
失敗回数を 0 に戻すのは次の 3 経路だけにした。

1. ログイン成功（正当な利用者だと確認できたとき）
2. パスワード変更
3. 管理者による解除（v376.78）

`memberLogin_` と `resolvePasswordAuthContextByLoginId_` の両方を揃えた。
後者は**パスワード再設定の導線を叩くだけでカウントを消せる**状態だった。

### テストの穴（同じ見落としを繰り返さないために）

既存の `test:login-lockout` は**各関数を単体で**検証しており、
「失敗 → ロック → 待機満了 → 再試行」という**状態遷移の連続**を通していなかった。
単体では正しく、つなげたときだけ破綻する典型で、v376.71 から今日まで気づけなかった。

状態遷移を実際に回すケースを 4 件追加（18 → 22）。**旧挙動へ戻すと 2 件が落ちる**ことを確認済み。

**教訓**: 段階的にふるまいが変わる機能は、単体テストに加えて**遷移をつないだテスト**を必ず置く。
