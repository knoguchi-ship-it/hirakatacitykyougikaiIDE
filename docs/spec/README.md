# 仕様書の読み方

> **ここが `docs/spec/` の入口です。** 本書は要件・設計の本文を持たない案内です。要件を決めたり変更したりするときは、必ず表中の正本へ記載してください。

## 1. まず知っておくこと

- 仕様の正本は、このフォルダの 5 文書です。内容を二重に書かず、担当領域の文書だけを更新します。
- [仕様トレーサビリティ一覧](../268_SPEC_TRACEABILITY_2026-09-04.md) は、要件 ID・検証方法・実装箇所をたどるための索引です。要件本文の正本ではありません。
- 現在の運用状態、リリース版、次に行う作業は [HANDOVER.md](../../HANDOVER.md) が正本です。仕様書に運用値やリリース履歴を複写しません。

## 2. 正本の役割分担

| 文書 | この文書で決めること | 読む場面 |
|---|---|---|
| [01 SOW](01_SOW.md) | 目的、対象範囲、非機能要件、リスク、未確定事項 | 要望を受けたとき、範囲や優先順位を判断するとき |
| [02 RD](02_RD.md) | 業務フロー、ユースケース、業務ルール、入力検証 | 業務上の振る舞い・承認・例外を変えるとき |
| [03 TRD](03_TRD.md) | 現行 GAS の技術構成、セキュリティ、GCP 移植条件 | API、認証、構成、性能、移植可能性を変えるとき |
| [04 UI/UX](04_UIUX.md) | 画面、遷移、表示条件、文言・操作・アクセシビリティ規約 | 画面や利用者操作を変えるとき |
| [05 データ・IF](05_DATA_IF.md) | データ規約、キー・型、API 契約、スキーマ変更手順 | 保存項目、API、CSV、データ移行を変えるとき |

## 3. 目的別の最短ルート

| 目的 | 読む順序 |
|---|---|
| 要望の受入れ・方針決定 | SOW の該当範囲 → RD の該当ユースケース・業務ルール → 未確定事項 |
| 画面を改修する | RD の該当ルール → UI/UX の該当 `SCR-xx` → データ・IF（保存またはAPIが変わる場合） |
| バックエンドを改修する | RD の該当ルール → データ・IF → TRD 第1部（現行 GAS） |
| 認証・権限・外部連携を改修する | SOW のセキュリティ要件 → RD → TRD → データ・IF |
| GCP 移行を検討する | TRD 第2部 → [GCP移行計画](../250_GCP_MIGRATION_PARALLEL_RUN_PLAN_2026-07-07.md) |
| 要件・実装・テストの対応を確認する | [仕様トレーサビリティ一覧](../268_SPEC_TRACEABILITY_2026-09-04.md) → 該当する正本 |
| リリースや本番運用を行う | [HANDOVER.md](../../HANDOVER.md) → [デプロイ方針](../09_DEPLOYMENT_POLICY.md)。仕様書だけで判断しない |

## 4. 変更時のルール

1. 変更する内容が「なぜ・何を」なら SOW、「業務上どう動くか」なら RD、「どう作るか」なら TRD、「画面でどう見せるか」なら UI/UX、「何を保存・送受信するか」ならデータ・IFへ記載します。
2. 複数領域に影響する場合は、それぞれの正本を最小限更新し、[仕様トレーサビリティ一覧](../268_SPEC_TRACEABILITY_2026-09-04.md) に要件 ID と検証方法を追加します。
3. 同じルールや値を別の仕様書に複写しません。必要な場合は、正本の節へリンクします。
4. 画面 ID は UI/UX、業務ルール ID は RD、技術・移行判断は TRD にのみ定義します。
5. 未確定の事項は SOW の未確定事項へ集約します。推測で仕様化しません。

## 5. 全体レビューをするとき

全仕様の矛盾を確認するレビューでは、次の順に読みます。

1. SOW
2. RD
3. UI/UX
4. データ・IF
5. TRD
6. 仕様トレーサビリティ一覧

日常の改修では、上記の全通読は不要です。第3節の目的別ルートに従い、影響する正本だけを読みます。

## 6. 現行と将来の区別

[TRD](03_TRD.md) は、第1部が現在稼働している GAS 構成、第2部が将来の GCP 移行後の構成です。日常の GAS 改修では第1部を正とし、第2部は GCP 移植可能性の確認に使用します。
