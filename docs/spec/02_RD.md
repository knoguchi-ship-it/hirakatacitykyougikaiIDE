## 1. システム概要

- **システムの目的**
  会員名簿・年会費・研修・役員/請求・広報発送の事務を Web 化し、紙と Excel の手作業を削減する。
  会員自身が情報を更新できるようにして、事務局への転記を無くす。

- **対象ユーザー**
  ①事務局（管理ポータル） ②会員（会員マイページ） ③一般・非会員（公開ポータル）。

- **利用シーン**
  - 入会希望者が協議会サイトから申込む（随時）
  - 事務局が申請を確認して承認する（随時）
  - 会員が研修を探して申込む（研修の募集期間中）
  - 事務局が年会費の納入状況を更新する（年度初〜）
  - 事務局が広報誌の宛名リストを出力する（発送のつど）
  - 会員が勤務先や連絡先の変更を届け出る（随時）

- **現行業務との差分**
  | 項目 | 従来 | 本システム |
  |---|---|---|
  | 入会 | 紙の入会申込書を郵送・持参 | 公開ポータルから Web 申請。承認と同時に会員マイページの認証情報を自動発行 |
  | 変更届 | 紙の変更届 | 会員マイページ、または公開ポータル（本人確認コードで認証）から申請 |
  | 名簿 | Excel を手作業で更新 | DB を正本にし、必要なレイアウトで出力 |
  | 研修申込 | FAX・メール | 会員は マイページ、非会員は公開ポータルから申込 |
  | 年会費 | Excel 管理 | 年度ごとの納入状況を画面で管理し、会員マイページにも表示 |
  | 広報発送 | 手作業で宛名作成 | 発送区分で抽出して宛名リストを出力 |

## 2. 対象ユーザーとロール

権限の割当（どのロールがどのメニューを使えるか）は **SOW §3.2 が正本**。本節は**業務上の役割**を定義する。

| ロール | 利用目的 | 参照範囲 | 操作可能範囲 | 禁止操作 |
|---|---|---|---|---|
| MASTER | システム全体の管理。権限とデータの最終責任 | 全データ | 全操作（権限管理・データ管理を含む） | — |
| 管理者（事務局） | 日常の会員事務 | 全会員・全研修・全申請 | 会員/申請/年会費/研修/請求/役員/名簿/メールの各操作 | データ管理（削除・復元）は不可 |
| 研修管理者 | 研修運営 | 研修と申込者 | 全研修の作成・編集・名簿・出欠 | 会員情報・年会費・請求 |
| 研修登録者 | 研修の登録のみ | 研修と申込者 | **自分が登録した研修のみ**編集可 | 他者が登録した研修の編集 |
| 一般（予約） | 現在は管理ログインを想定しない | 共通機能のみ | — | — |
| 個人会員 | 自分の情報管理と研修申込 | 自分の情報・自分の申込・自分の年会費 | 自己情報の更新、研修申込/取消、退会申請、請求提出 | 他会員の情報 |
| 事業所会員 代表者 | 事業所と所属職員の管理 | 自事業所と所属職員 | 事業所情報の変更、職員の追加・除籍、自身の研修申込 | 他事業所の情報 |
| 事業所会員 管理者（職員） | 代表者に準じる管理 | 自事業所と所属職員 | 代表者に準じる（詳細は U-15） | 他事業所の情報 |
| 事業所会員 メンバー（職員） | 自身の研修申込のみ | 自事業所の情報は**閲覧のみ** | 自身の研修申込・自己情報 | 事業所情報・他職員の情報の変更 |
| 賛助会員 | 協議会の支援 | 自分の情報 | 自己情報の更新、退会申請 | 研修申込の可否は U-16 |
| 非会員（一般） | 入会申込・研修の外部申込 | 公開情報のみ | 各種申請、研修の外部申込・取消 | 会員情報の参照 |

**議決権**（総会運営）: 事業所会員は**所属メンバー 1 人につき 1 議決権**（2026-09-03 確定）。
会費は 1 事業所あたりの定額のため、**会費の単位（事業所）と議決権の単位（人）が異なる**。
賛助会員の議決権と、議決権を持つ「人」の範囲は**未確定**（SOW U-01）。**システムには議決権の概念が無い**。

## 3. 業務フロー

### 3.1 通常フロー

**A. 入会（個人・賛助）**
1. 申込者が公開ポータルで重要事項を確認する
2. 会員種別を選び、基本情報・住所・連絡設定を入力して申込む
3. システムが申請を受け付け、申込者へ受付確認メールを送る
4. 事務局が管理ポータルの「変更申請管理」で内容を確認し、**承認**する
5. システムが会員レコードと認証アカウントを作成し、初期パスワードを含む案内メールを送る
6. 会員がマイページにログインし、パスワードを変更する

**B. 入会（事業所）**
1〜3 は A と同じ（入力は事業所情報＋所属職員一覧、代表者を 1 名指定）
4. 事務局が承認する
5. システムが事業所の会員レコードと**職員ごとの認証アカウント**を作成し、代表者向け・メンバー向けの案内メールを**それぞれの文面**で送る

**C. 登録情報の変更**
1. 会員がマイページから変更する（即時反映）／または公開ポータルから申請する
2. 公開ポータル経由の場合、登録メールアドレスへ**本人確認コード**を送り、入力を確認する
3. 申請として登録され、事務局が承認すると反映される

**D. 退会**
1. 会員（または公開ポータル）から退会を申請する
2. 事務局が承認する
3. 退会日を記録し、**当年度末での退会として扱う**
4. 退会日の翌年 4/1 到達時に削除フラグを自動適用する（履歴は保持）

**E. 研修**
1. 事務局（または研修管理者）が研修を登録し、公開する
2. 会員はマイページから、非会員は公開ポータルから申込む
3. 事務局がリマインダーを送る／名簿を出力する／出欠を記録する

**F. 年会費**
1. 事務局が年度ごとの納入状況を登録・更新する
2. 未納の会員には、マイページに納入案内と振込先が表示される

**G. 広報発送**
1. 事務局が発送区分（広報誌発送／広報誌のみ／お知らせ発送）を選ぶ
2. 対象を抽出して宛名リストを出力する

### 3.2 例外フロー

| No | 例外 | 発生条件 | 対応 |
|---|---|---|---|
| 1 | 申請の却下 | 事務局が内容に不備を認めた | 却下理由を添えて通知。申請は `REJECTED` で保持 |
| 2 | 処理済み申請の再処理 | 承認/却下済みの申請に再度操作 | 「すでに処理済み」として拒否する |
| 3 | 重複会員の発生 | 同じ介護支援専門員番号で二重登録 | 重複修復（人物統合）で 1 人に統合し、履歴をログへ記録 |
| 4 | 個人 ⇄ 事業所職員の移行 | 転職等 | 旧会員を `TRANSFERRED` にし移行日を記録。ログイン ID・認証・役員・振込口座・請求・研修申込を移行先へ引き継ぐ |
| 5 | 本人確認コードの誤入力 | 公開ポータルの変更・退会申請 | 5 回まで。超過はレート制限 |
| 6 | ログイン失敗の連続 | 会員ログイン | 連続失敗でカウントし、成功で 0 に戻る。段階的に待機時間を設ける（**未実装**・SOW U-03） |
| 7 | メールの送信不可 | 全体停止スイッチが無効／種別が無効／宛先未登録 | 送信せず、抑止理由をログに記録する。画面には成功と表示しない |
| 8 | 添付が上限超過 | 一括メール・研修メール | 送信前にエラーで止める（Drive リンクへの自動置換に委ねない） |
| 9 | 退会時に年会費が未納 | 退会申請 | **規程では納入をもって手続完了**だが、システムに未納チェックが無い。現在は事務局が 3 月末に手作業で確認（SOW U-07） |
| 10 | 会員の削除 | 事務局がデータ管理から削除 | 会員系テーブルの行をアーカイブへ移動し、削除バッチ単位で復元できる。ログイン履歴のみ物理削除 |
| 11 | 研修の申込上限超過 | 定員に達した | 申込を受け付けない |
| 12 | 事業所の職員数が上限超過 | 職員追加 | 全体既定の上限、または事業所ごとの個別上限で判定して拒否 |

## 4. ユースケース詳細

本節では**中核となる 6 つ**を詳細化する。残りは §4.7 の一覧に列挙し、**未詳細であることを明示**する
（推測で埋めない）。入力項目は**キー名のみ**を示し、型・制約はデータ・IF 定義書を参照する。

### UC-001: 入会申込（個人・賛助）

| 項目 | 内容 |
|---|---|
| アクター | 非会員（申込者） |
| 事前条件 | 公開ポータルにアクセスできる。重要事項の確認にチェックしている |
| トリガー | 「新規入会を申し込む」を選択 |
| 事後条件 | 申請が `PENDING` で登録され、申込者へ受付確認メールが送られる |
| 権限条件 | 認証不要（匿名） |

**基本フロー**
1. 重要事項（規程）を表示し、確認のチェックを求める
2. 会員種別を選ぶ（年会費が表示される）
3. 基本情報（氏名・カナ・介護支援専門員番号）を入力する
4. 勤務先・自宅の住所、連絡先、連絡方法の希望を入力する
5. 入力内容を確認して送信する
6. 申請を登録し、受付確認メールを送る

**入力項目**（キー名のみ。詳細はデータ・IF 定義書）

| 項目名 | キー名 | 必須 | 備考 |
|---|---|---|---|
| 会員種別 | `memberType` | ○ | 個人 / 賛助 |
| 姓・名 | `lastName` / `firstName` | ○ | |
| セイ・メイ | `lastKana` / `firstKana` | ○ | 全角カタカナ |
| 介護支援専門員番号 | `careManagerNumber` | 個人は○ | **会員マイページのログイン ID になる** |
| 勤務先情報 | `officeName` / `officePostCode` / `officePrefecture` / `officeCity` / `officeAddressLine` / `officeAddressLine2` / `phone` / `fax` | 一部○ | |
| 自宅情報 | `homePostCode` / `homePrefecture` / `homeCity` / `homeAddressLine` / `homeAddressLine2` / `mobilePhone` | 一部○ | |
| メールアドレス | `email` | ○ | 通知の宛先 |
| 連絡方法の希望 | `mailingPreference` | ○ | メール / 郵送 |
| 郵送先の希望 | `preferredMailDestination` | ○ | 自宅 / 勤務先 |

**出力項目**

| 項目名 | 説明 |
|---|---|
| 申請 ID | 受付番号として受付確認メールに記載 |
| 受付日時 | |
| 完了画面の案内 | 表示内容は設定で変更できる（UI/UX 定義書） |

### UC-002: 入会申込（事業所）

| 項目 | 内容 |
|---|---|
| アクター | 非会員（事業所の担当者） |
| 事前条件 | UC-001 に同じ |
| トリガー | 会員種別で「事業所会員」を選択 |
| 事後条件 | 申請が `PENDING` で登録され、**代表者のメールアドレス**へ受付確認メールが送られる |
| 権限条件 | 認証不要 |

**基本フロー**
1〜2 は UC-001 と同じ
3. 事業所情報（事業所名・事業所番号・住所・電話）を入力する
4. 所属職員を登録する（**1 名を代表者に指定**。職員ごとに氏名・カナ・介護支援専門員番号・メール・区分・メール配信の有無）
5. 確認して送信する

**業務ルール**
- 職員の**介護支援専門員番号がその職員のログイン ID になる**
- 職員の区分は 代表者 / 管理者 / メンバー の 3 種
- **受付確認メールの宛先は代表者のメールアドレス**。代表者が不在、またはメール未入力の場合は**宛先を決めずに送信しない**（誤送信を避けるため）
- 登録できる職員数は、全体既定の上限または事業所ごとの個別上限で制限する

### UC-003: 変更申請の承認／却下

| 項目 | 内容 |
|---|---|
| アクター | 事務局（管理者・MASTER） |
| 事前条件 | 管理ポータルにログイン済み。対象の申請が `PENDING` |
| トリガー | 「変更申請管理」で申請を開き、承認または却下を選ぶ |
| 事後条件 | 申請が `APPROVED` / `REJECTED` になり、申請者へ通知が送られる |
| 権限条件 | `change-requests` メニューの権限 |

**基本フロー（承認）**
1. 申請の内容（申請種別・申請者・変更内容）を表示する
2. 承認を実行する
3. 申請種別に応じて実データへ反映する
   - 入会申込 → 会員レコードと認証アカウントを作成し、認証情報メールを送る
   - 登録情報変更 → 会員/事業所の情報を更新する
   - 退会 → 退会日を記録する
   - 職員追加 → 職員レコードと認証アカウントを作成する
   - 職員除籍 → 職員を除籍状態にする
4. 処理日時・処理者を記録し、申請者へ承認通知を送る

**例外**: 既に処理済みの申請は「すでに処理済みです」として拒否する（二重処理の防止）。

**業務上の承認者**: 定款では**理事会の承認**、公開サイトでは**役員の承認**と記載されている。
システム上の承認操作は事務局が行っており、**この操作が業務上の承認そのものなのか、決定の代行入力なのかは未確定**（SOW U-01 関連・台帳 D-04）。

### UC-004: 研修の申込（会員）

| 項目 | 内容 |
|---|---|
| アクター | 会員（個人・賛助・事業所職員） |
| 事前条件 | 会員マイページにログイン済み。対象研修が受付中 |
| トリガー | 研修一覧から「申し込む」 |
| 事後条件 | 申込が登録され、確認メールが送られる（種別が有効な場合） |
| 権限条件 | 会員セッション。**申込は職員ごと**（事業所単位ではない） |

**基本フロー**
1. 受付中の研修を一覧表示する
2. 詳細（日時・会場・案内 PDF）を確認する
3. 申込む（定員に達している場合は受け付けない）
4. 申込確認メールを送る

**取消**: 会員は自分の申込を取り消せる。取消可否の期限は U-17（未確定）。

### UC-005: 一括メール送信

| 項目 | 内容 |
|---|---|
| アクター | 事務局 |
| 事前条件 | 管理ポータルにログイン済み。メールの全体停止スイッチが有効 |
| トリガー | 「一括メール送信」で対象を抽出し、本文を作成して送信 |
| 事後条件 | 対象者へ送信され、送信ログと明細が残る |
| 権限条件 | `bulk-mail` メニューの権限 |

**基本フロー**
1. 会員種別・在籍状態などで対象を抽出する
2. 件名・本文を入力する（差し込みタグを使える）
3. 添付を指定する（共通添付／Drive からの自動添付／個別添付）
4. 送信前に**配信方法**（通常送信／テスト集約／送信抑止）を確認する
5. 送信し、結果を表示する

**業務ルール**
- 差し込みは受信者ごとに行う（氏名・事業所名・会員番号）
- **配信方法が「テスト集約」のときは画面上部に警告を表示する**（過去に全メールが検証用アドレスへ集約されたまま運用された事故があるため）
- 抑止された分は**成功件数に数えない**
- 添付の合計が上限を超える場合は送信前にエラーで止める
- **1 日の送信通数には上限がある**ため、全会員への一斉送信は 1 日 1 回を限度とする

### UC-006: 会員の削除（データ管理）

| 項目 | 内容 |
|---|---|
| アクター | MASTER |
| 事前条件 | 削除対象を検索して特定している。**バックアップを取得済み** |
| トリガー | データ管理コンソールで削除を実行 |
| 事後条件 | 会員系データがアーカイブへ移動し、削除ログが残る |
| 権限条件 | `data-management` メニュー（**MASTER 限定**） |

**基本フロー**
1. 対象を検索する
2. 削除内容をプレビューする（移動対象の件数を表示）
3. 最終確認のうえ実行する
4. 会員系テーブルの行を live から `*_archive` へ**移動**する
5. ログイン履歴は**物理削除**する
6. 削除ログ（バッチ ID・対象・実行者・削除前スナップショット）を残す

**復元**: 同一の削除バッチ ID の全行を live へ戻すことで、**会員単位でまとめて復元**できる。

## 5. フロントエンド機能

- **画面一覧・遷移・フォーム項目・通知文言**: **UI/UX 画面遷移定義書が正本**（本書では扱わない）
- **業務上の要求**（RD として定めるもの）
  1. 公開ポータルは**匿名で完結**し、会員情報を参照させない
  2. 入会申込は**種別選択 → 入力 → 確認 → 完了**の 4 段階とし、確認画面で全項目を見せる
  3. 会員マイページは、**自分の情報・自分の申込・自分の年会費**のみを表示する
  4. 管理ポータルは**メニュー単位で表示を切り替える**（権限の無いメニューは表示しない）
  5. スマートフォンで完結できること（**事務局も外出先で確認する**）

## 6. バックエンド機能

- **技術構成・実装方式**: **TRD が正本**（本書では扱わない）
- **業務上の要求**（RD として定めるもの）

| 機能 | 業務上の要求 |
|---|---|
| 計算ロジック | 会計年度（4/1〜3/31）に基づく在籍判定。年会費は**会員種別ごとの設定値**を用いる |
| データ保存 | 事務局が内容を確認できる形で保存する |
| 外部連携 | メール送信、ファイルの保管・添付 |
| 監査ログ | 管理操作の実行者・対象・日時を残す |
| バッチ処理 | 案内 PDF のサムネイル生成（定期実行） |
| 通知処理 | 申請の受付・承認・却下、認証情報の発行、研修の確認・リマインダー、本人確認コード、パスワード再設定 |
| リトライ | メール送信の失敗は個別に記録し、**全体を止めない** |

## 7. セキュリティ要件

**正本は SOW §3**（認証・認可・ログ）。本節では**業務要件としての補足**のみを記す。

1. 会員に Google アカウントの保有を強制しない（保有していない会員がいるため）
2. 事務局の権限は**担当業務に応じて分けられる**こと（研修だけを担当する人に会員情報を見せない）
3. 誤送信を防ぐ仕組みを持つこと（過去に実害があったため）
4. 削除は**取り消せる**こと（誤操作からの復旧）
5. 個人情報の保持期間は**未設定**（SOW U-02）

## 8. 非機能要件

**正本は SOW §5**。本書では再掲しない。
