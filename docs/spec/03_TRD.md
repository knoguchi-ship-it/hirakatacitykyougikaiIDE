# 第1部: 現行（Google Apps Script）

## 1. アーキテクチャ概要

- **フロントエンド**: React 19 + TypeScript。Vite で**単一 HTML へインライン化**し、deflate-raw で圧縮して配信する
- **バックエンド**: Google Apps Script（V8 ランタイム）。`processApiRequest(action, payload)` の**単一エンドポイント**
- **データベース**: Google スプレッドシート（業務データ）＋ 別スプレッドシート（ログ）
- **ストレージ**: Google Drive（研修案内 PDF・請求添付・一括メールの添付）
- **外部 API**: Gmail（送信）、Drive（ファイル・サムネイル）、Cloud Run（パスワードハッシュ・**現在は無効**）
- **認証基盤**: Google アカウント（管理）／自前のパスワード認証（会員）／匿名（公開）
- **管理機能**: 同一コードベースから **admin 専用ビルド**を生成して別プロジェクトへ配信

### 1.1 3 プロジェクト分離（この構成の中核）

同一の `gas-src` から**3 つの Apps Script プロジェクト**をビルドし、それぞれ別に配信する。

| プロジェクト | 配信対象 | Web アプリのアクセス設定 | OAuth スコープ数 |
|---|---|---|---|
| 統合 public | 公開ポータル（＋旧会員ポータル URL） | `ANYONE_ANONYMOUS` | 8 |
| member split | 会員マイページ | `ANYONE_ANONYMOUS` | 8 |
| admin split | 管理ポータル | **`DOMAIN`** | 9（`gmail.settings.basic` が追加） |

- 実行者はいずれも `USER_DEPLOYING`（デプロイしたアカウントの権限で実行）
- **ビルド時に、そのプロジェクトが受け付けない action と関連コードを削除する**。公開ビルドには管理用の処理そのものが含まれない
- 各プロジェクトの許可 action は許可リストで管理し、**リリース前ゲートで機械検査**する

### 1.2 リクエストの流れ

```text
ブラウザ（React SPA・GAS の iframe 内）
  │  services/api.ts（transport 抽象）
  ↓  google.script.run.processApiRequest(action, JSON payload)
Apps Script
  │  ① 境界チェック（このプロジェクトが受け付ける action か）
  │  ② 認証（管理=Google セッション / 会員=セッションキャッシュ / 公開=なし）
  │  ③ 認可（action → menu → role.allowedMenus）
  │  ④ 業務処理（キャッシュ → スプレッドシート）
  ↓  JSON 文字列（{ success, data } / { success:false, error }）
ブラウザ
```

- **フロントは `google.script.run` を直接呼ばない**。`services/api.ts` の transport 抽象を必ず経由する
  （移行時に通信方式だけを差し替えられるようにするため。2026-07 に分離済み）

### 1.3 起動時の処理（配信の工夫）

GAS は外部アセットの配信に向かないため、**JS/CSS を 1 つの HTML に埋め込み、圧縮して配信**している。
起動ローダーは次を必ず備える（欠けると iOS Safari で初回に白画面になる事故が実際に発生した）。

1. CSS のみで描画する起動スプラッシュ（JS 評価前から見える）
2. 全体を try/catch で囲み、失敗時は「再読み込みする」ボタン付きのエラー表示に切り替える（無言で失敗しない）
3. 解凍 API の対応判定（未対応ブラウザには更新を促す）
4. 不要な importmap の除去
5. Web フォントの非ブロック化
6. 解凍と評価を待機時間に分散し、スプラッシュを止めない

### 1.4 認証の原則（principal の決め方）

**「今この操作をしているのは誰か」を、どこから決めるか**を 1 か所に固定する。ここがぶれると他人のデータに触れる。

- 会員側は `T_認証アカウント`（認証方式 = パスワード）の**ログイン ID に紐づく行**を基準に判定する
- 管理側は Google アカウント認証とホワイトリスト照合を基準に判定する
- **現在の紐付けは `T_認証アカウント` の行が正本**。`T_管理者Googleホワイトリスト.紐付け会員ID` は
  後方互換のための参照補助であり、認証行の会員 ID より優先しない
- **`loginId` を単一の概念として混用しない**。会員側の再読込アンカーはパスワードのログイン ID、
  管理者セッションの識別子は Google メールとして分離する
- 管理者ログイン中に会員マイページを表示する場合、再読込の主キーは**会員ID／職員ID を正**とし、
  Google メールを会員データ取得の `loginId` に渡さない
- 会員セルフサービスの API は、**クライアントが送ってきた会員 ID を認可根拠に使わない**。
  ログイン ID から解決した認証行の会員ID／職員IDを正本の principal とする（データ・IF 定義書 §5.5）

### 1.5 パスワードの保存と再設定

**保存**

- 新規保存は**バージョン付き PBKDF2-HMAC-SHA256 ＋ 検証側 pepper**。旧方式（SHA-256・旧 PBKDF2）は
  ログイン成功時に順次移行する
- **pepper は DB に保存しない**。Script Property に置き、3 プロジェクトへ**同一値**を設定する
  （未設定のプロジェクトがあるとリリース不可）
- pepper の値は Git・引継ぎ資料・文書・ログ・チャット・生成物のいずれにも残さない（`AGENTS.md` §0）
- `.env` は Apps Script の本番実行時に参照されないため、**本番の正本にしない**

**再設定**

- ログイン画面に「パスワードを忘れた方」の導線を置く
- 識別子は**ログイン ID ＋ 登録メールアドレス**。職員アカウントの登録メールは `T_事業所職員.メールアドレス`、
  会員のみのアカウントは `T_会員.代表メールアドレス` が正本
- 応答は**登録の有無や照合結果を漏らさない共通文言**に統一する
- メールで送るのは短時間有効な**確認コード**のみ。**平文パスワードをメールで送らない**
- 確認コードはサーバー側でハッシュ化して短期キャッシュに置き、成功時または試行回数の上限で破棄する
- 再設定に成功したら、ハッシュ・ソルト・更新日時を更新し、**ログイン失敗回数とロック状態をリセット**する

### 1.6 起動から表示までのデータ取得順序

固定オーバーヘッド（§6）が大きいため、**必要なものだけを、必要な順に取る**。

| 段階 | 取得するもの |
|---|---|
| 未認証 | 認証設定だけを取り、ログイン画面を先に出す |
| 管理者ログイン直後 | ダッシュボードと設定（1 回の呼び出しにまとめた統合 API）。集計と一覧サマリだけを先に出す |
| 研修管理 | 研修一覧だけを読む（会員データは読まない） |
| 会員マイページ／研修申込 | 会員単位の軽量 API で、その会員の情報と研修一覧だけを取る |
| 管理者が会員詳細などへ進んだとき | ここで初めて全件を読む |

取得したデータは画面のルートで保持し、子コンポーネントへ渡す。
更新後は**サーバーの応答を待ってから**ローカルの状態とキャッシュを同期する。

| 領域 | 採用技術 | バージョン | 選定理由 | 代替案 | 採用しない案 |
|---|---|---|---|---|---|
| フロント | React + TypeScript | React 19.2 / TS 5.8 | 画面数が多く状態管理が必要。型で DB 列との対応を守る | Vue / 素の JS | jQuery 系（保守性） |
| スタイル | Tailwind CSS | 4.2 | レスポンシブを規約として強制しやすい | CSS Modules | 独自 CSS（規約が守られない） |
| ビルド | Vite ＋ singlefile プラグイン | Vite 6.2 / plugin 2.3 | GAS へ 1 ファイルで配信するため | webpack | 複数ファイル配信（GAS で不利） |

| メール | Gmail（`MailApp` / `GmailApp`） | — | 送信元エイリアスを使うため GmailApp が必要 | 外部メール API | 各所からの直接送信 |
| ファイル | Google Drive（Advanced Drive Service v3） | v3 | Workspace の共有設定をそのまま使える | Cloud Storage | 外部ストレージ |
| 帳票 | ブラウザ印刷（PDF）／Excel 出力 | — | サーバー側 PDF 生成を持たずに済む | Docs テンプレ変換 | **Docs 差し込み**（移植性が低い。§4.8 の NG） |
| デプロイ | clasp（固定 deployment を版更新） | clasp 3.2 | URL を変えずに版だけ差し替える | 新規 deploy | **`clasp deploy`（URL が変わるため全面禁止）** |
| 文面生成（任意機能） | Gemini API（`@google/genai`） | — | 事務局の案内メール下書きを補助する。**業務判断には使わない** | 手書き | 送信内容の自動確定 |
| テスト | Node test runner ＋ Playwright ＋ axe-core | Playwright 1.59 | 実ブラウザで 3 ポータルを検証 | Jest | 手動確認のみ |

### 2.1 OAuth スコープ（境界ごとに最小化）

3 プロジェクトで共通に持つのは 8 スコープ（`openid` / スプレッドシート / 外部リクエスト / メール送信 / Gmail 送信 / Drive / userinfo.email / cloud-platform）。
**admin だけが `gmail.settings.basic` を追加で持つ**（送信元エイリアスの一覧取得のため）。
スコープを増やす変更は 3 プロジェクトすべてで再同意が必要になるため、**追加は最小限に留める**。

## 3. データ設計

| 項目 | 方針 |
|---|---|
| データ保存方針 | 1 テーブル = 1 シート。1 行 = 1 レコード。**業務キーは必ず ID 列**とし、行番号・セル位置に依存しない |
| 正規化方針 | マスタ（`M_*`）と業務テーブル（`T_*`）を分離。コード値はマスタを参照する。表示ラベルはマスタの名称を正とする |
| 履歴管理 | 変更履歴が必要なもの（年会費・人物統合・削除）は**専用の履歴テーブル**へ追記する（追記のみ・更新しない） |
| 論理削除 | 通常は `削除フラグ` による論理削除。**ただし管理者の削除操作はアーカイブ移動**（§3.1） |
| バックアップ | 破壊的操作の前にスプレッドシートを複製する（手順は運用文書） |
| データ保持期間 | **未設定**（SOW U-02）。アーカイブは無期限に残る |
| スキーマ変更 | `テーブル定義` を正本に、起動時の初期化処理が列を追加・整列する。**列の追加は名前ベースで既存データを保持**する |
| ER 図 | `テーブル定義` ＋ メタデータから**自動生成**する（手書き禁止）。ドリフトはゲートで検出 |

### 3.1 削除の設計（アーカイブ移動）

- 会員系テーブルの行を live から `<テーブル名>_archive` へ**移動**する（コピーではなく移動）
- 各アーカイブ行に **アーカイブ ID・削除バッチ ID・アーカイブ日時**の 3 列を付与する
- **削除バッチ ID = 削除ログの ID**。同一バッチの全行を戻すことで**会員単位でまとめて復元**できる
- ログイン履歴だけは**物理削除**する（件数が多く、個人情報を残す必要がないため）
- 新しく会員に紐づくテーブルを追加した場合は、**アーカイブ対象の一覧と照合条件の両方に登録する**（登録漏れは孤児データになる）

### 3.2 キャッシュ設計

| 項目 | 設計値 | 根拠 |
|---|---|---|
| 1 キーの上限 | **90 KB** | 公式上限 100 KB に 10% のマージン |
| 総キー数 | **200 以内** | 公式の件数上限 1,000 の 20%。超過時は**有効期限が最も遠い 900 件を残す**仕様のため、余裕を確保する |
| 総サイズ | **1.5 MB 以内** | 現状実測 約 500 KB の 3 倍を許容 |
| TTL | **300 秒** | 書き込み時に無効化するため長期保持は不要 |
| 前提 | **消えてもよい設計にする** | 合計サイズの保証が無く予告なく捨てられるため、**キャッシュミス時は DB から再構築できること**が必須 |

## 4. 計算アルゴリズムと責務分担

| 処理 | フロント | バックエンド | DB | 備考 |
|---|---|---|---|---|
| 入力チェック | ○（即時フィードバック） | **○（最終判定）** | — | フロントの検証は UX のため。**サーバー側の検証を必ず通す** |
| 権限チェック | △（メニュー表示の制御） | **○（強制）** | — | 画面の非表示は単独の防御にしない |
| 会計年度の在籍判定 | ○ | ○ | — | **同一の共有モジュール**をフロントと GAS の双方が使う（値のぶれを防ぐ） |
| 年会費の金額決定 | — | ○ | ○（マスタが正本） | 種別ごとの金額はマスタから読む |
| 集計（ダッシュボード） | — | ○ | — | 全件読込のうえサーバー側で集計。結果をキャッシュ |
| 検索・絞り込み | ○（クライアント側フィルタ） | — | — | 全件をフロントへ渡してから絞る。**かな検索も純粋なクライアント処理** |
| 通知（メール） | — | ○ | — | 単一の出口を通す |
| ログ記録 | — | ○ | ○ | 監査・送信・ログイン・削除 |
| 帳票の生成 | ○（印刷/Excel 生成） | △（データ供給） | — | サーバー側 PDF 生成を持たない |

### 4.1 単一情報源（値・判定を 2 箇所で決めない）

フロントと GAS で同じ判定が必要なものは、**共有モジュールを 1 つ置き、GAS へはビルド時に注入**する。

| 対象 | 共有方法 |
|---|---|
| 会計年度の在籍判定 | 共有モジュール → ビルド注入 |
| 会員種別のラベル・年会費の既定値・金額整形 | 共有モジュール → ビルド注入 |
| RBAC の action → menu | 共有モジュール → ビルド注入 |
| 入力検証パターン | 共有モジュール（フロント）。GAS 側は各関数内に置く（ビルド時の削除を避けるため）。**変更時は同時更新** |
| メール差し込みタグのカタログ | 共有モジュール（UI が参照） |

逸脱はリリース前ゲートで検出する。

### 4.2 メール送信の設計

- **出口は 1 つだけ**。すべてのメールが同一の関数を通り、そこで次を順に判定する
  1. 種別ごとの有効／無効
  2. 全体停止スイッチ
  3. 配信方法（通常送信／テスト集約／送信抑止）
  4. 未解決の差し込みタグの除去（残っていればログに記録して取り除く）
- 送信元エイリアスを使う場合のみ `GmailApp`、それ以外は `MailApp`（スコープの都合）
- 抑止された送信は**成功に数えない**

## 5. 外部 API 連携仕様

### API-001: Gmail（メール送信）

| 項目 | 内容 |
|---|---|
| 用途 | 自動通知・一括メール・研修メールの送信 |
| 認証方式 | Apps Script の実行アカウント権限（`gmail.send` / `script.send_mail`） |
| エンドポイント | `MailApp.sendEmail()` / `GmailApp.sendEmail()`（サービス経由） |
| レート制限 | **送信通数に 1 日あたりの上限がある**（アカウント種別により異なる。Workspace は管理者設定） |
| タイムアウト | Apps Script の実行時間（1 実行あたり 6 分）に含まれる |
| リトライ | **しない**。失敗は個別に記録し、他の宛先の送信を止めない |
| フォールバック | 送信元エイリアスが使えない場合は既定の送信元にする |

### API-002: Google Drive（ファイル・サムネイル）

| 項目 | 内容 |
|---|---|
| 用途 | 研修案内 PDF の保管とサムネイル、請求の添付、一括メールの自動添付 |
| 認証方式 | 実行アカウント権限（`drive`） |
| エンドポイント | DriveApp ／ Advanced Drive Service v3 |
| レート制限 | Drive API のクォータに従う |
| タイムアウト | 実行時間に含まれる |
| リトライ | サムネイル生成は**定期実行で後追い修復**する（生成が遅れて空になることがあるため） |
| フォールバック | サムネイルが無い場合はプレースホルダを表示する |

### API-003: Cloud Run（パスワードハッシュ・**現在無効**）

| 項目 | 内容 |
|---|---|
| 用途 | Argon2id によるパスワードハッシュの生成・検証 |
| 認証方式 | ID トークン（実行アカウントの ID トークンを付与し、受信側で audience を検証） |
| エンドポイント | Cloud Run のサービス URL（値は Script Properties。**文書に書かない**） |
| レート制限 | 呼び出しはログイン・パスワード変更・資格情報発行の時のみ |
| タイムアウト | 実測 生成 646ms / 検証 315ms |
| リトライ | しない |
| フォールバック | **フラグが無効なら従来の PBKDF2 のみで動作**する（現状はこのモード） |

**Request（例）**

```json
{ "action": "hash", "password": "***", "pepperVersion": "v1" }
```

**Response（例）**

```json
{ "status": "success", "data": { "phc": "argon2id$v=19$m=...,t=...,p=..." } }
```

> パスワード・pepper の実値は**ログにも文書にも残さない**（`AGENTS.md` §0）。

## 6. パフォーマンス設計

| 項目 | 想定 | 対策 |
|---|---|---|
| データ量 | 会員 222・職員 157・研修 数件（2026-07-11 実測）。スプレッドシートのセル数は上限に対し十分な余裕 | 現状は問題なし |
| 同時利用者数 | 事務局の数名＋会員の随時アクセス | Apps Script の同時実行上限（1 ユーザーあたり 30）に対し余裕あり |
| レスポンス目標 | 公開 3 秒以内・管理 12 秒以内（SOW §5） | 下記の対策を実施済み |
| **固定オーバーヘッド** | **1 呼び出しあたり 1.8〜5 秒**。応答が数十バイトでも約 2 秒 | **コード最適化では解決しない**。呼び出し回数を減らす設計（初期化時に必要データをまとめて取得）で緩和している |
| ページング | 会員一覧などはクライアント側で分割表示 | サーバー往復を増やさないため |
| キャッシュ | 画面データをキャッシュし、書き込み時に無効化 | §3.2 |
| 非同期化 | 起動時の解凍・評価を分散 | スプラッシュを止めないため |
| 実行時間 | 1 実行 6 分の上限 | 最大負荷の全件読込でも実測 3〜5 秒 |

**結論**: 現行アーキテクチャの応答時間は**固定オーバーヘッドが支配的**であり、**現状が実質的な上限**である。
体感を大きく改善するには技術基盤の移行が必要になる（第2部）。

# 第2部: GCP 移行後

> **本部の範囲**: 移行後の**目標構成と実装方式**。
> **移行の手順・順序・並走・ロールバック条件は `docs/250_GCP_MIGRATION_PARALLEL_RUN_PLAN_2026-07-07.md` が正本**であり、本書には再掲しない。
> 無料枠の実数値・実測値は台帳 `docs/261` T-01〜T-07 が取得元。本書はそこから導かれる**設計上の制約**だけを書く。

## 7. 移行の目的（なぜ移すのか）

第1部 §6 の結論のとおり、現行の応答時間は**呼び出し 1 回あたり 1.8〜5 秒の固定オーバーヘッド**が支配的で、
コード最適化では改善しない。加えて次の 2 点は GAS のままでは解消できない。

| # | 現行の限界 | 移行で解消されるか |
|---|---|---|
| 1 | 応答の固定オーバーヘッド（1.8〜5 秒） | ✅ 解消する。Cloud Run の HTTP 応答に置き換わる |
| 2 | **データの国内保管ができない** | ✅ 解消する。Workspace のデータリージョンは米国・欧州・指定なしの 3 択で**日本を選べない**（台帳 T-05）。GCP は東京を明示指定でき、追加費用も発生しない |
| 3 | 1 実行 6 分・同時実行 30 の上限 | ✅ 解消する |

**2 が実質的な移行理由**である。国内保管を要件とするなら GCP 移行が唯一の実現手段になる。

## 8. 目標構成

### 8.1 プロダクト対応表

| 現行（GAS） | 移行後 | 備考 |
|---|---|---|
| HtmlService による SPA 配信 | **Firebase Hosting** | 静的アセットのみ。**個人データを置かない**。CDN のためリージョンの概念を持たない |
| `google.script.run` → `processApiRequest` | **Cloud Run**（JSON API） | フロントは `ApiClient` インターフェース越しにしか呼ばない（`docs/250` §3 原則 3） |
| スプレッドシート DB | **Firestore**（`(default)` / `asia-northeast1` / Native） | 無料枠が適用されるのは `(default)` のみ。**ロケーションは作成後変更不可**で、既に東京で作成済み |
| ログ用スプレッドシート | **Firestore**（別コレクション）＋ **Cloud Logging** | 監査ログは Firestore、アプリケーションログは Cloud Logging |
| Script Properties（設定） | **Firestore の設定コレクション**＋ **Secret Manager**（機微値のみ） | Script Properties をデータストアとして使う設計は NG パターン（`AGENTS.md` §4.8） |
| CacheService | **Cloud Run のインメモリ**、必要なら Firestore の派生ドキュメント | §11.3 |
| GmailApp / MailApp | **Gmail API**（サービスアカウントのドメイン全体の委任） | §12 |
| Drive（添付・研修案内） | **Google Drive を継続**（Cloud Storage は凍結・台帳 T-06） | §13 |
| ブラウザ印刷による帳票 | **Cloud Run 上のヘッドレス Chrome** | §14 |
| 管理者の Google 認証 | **Firebase Authentication**（Google プロバイダ）＋ 既存の許可リスト | §10 |
| 会員のパスワード認証 | **Cloud Run `hcmn-member-auth`**（実装済み） | §10 |
| 時間主導トリガ | **Cloud Scheduler → Cloud Run** | 6 分制限が無くなる |

### 8.2 既に存在する GCP リソース（2026-09-03 実測・読み取りのみ）

| 種別 | 実測 |
|---|---|
| Firestore | `projects/hcmn-member-system-prod/databases/(default)` / `asia-northeast1` / FIRESTORE_NATIVE |
| Cloud Run（5 サービス・**すべて `asia-northeast1`**） | `hcmn-portal-api` / `hcmn-member-auth` / `hcmn-member-api` / `hcmn-password-hash` / `hcmn-billing-killswitch` |
| Cloud Storage | **業務用バケットなし**（GCP が自動作成した内部用 3 本のみ） |
| 予算 | `hcmn-phase0-alert` 月 500 円で稼働中 |

### 8.3 リージョン方針（台帳 T-05・確定）

**新規に作る GCP リソースはすべて `asia-northeast1`（東京）**とする。
Firebase Hosting だけは CDN 配信でリージョンを持たないため対象外だが、**個人データを置かない**ことで担保する。

### 8.4 リクエストの流れ

```
Browser
  -> Firebase Hosting        静的アセット（HTML / JS / CSS）
  -> Cloud Run (JSON API)    認証・業務処理
       -> Firestore          業務データ・監査ログ
       -> Secret Manager     pepper・API キー
       -> Gmail API          メール送信
       -> Drive API          添付ファイル
```

現行の 3 プロジェクト分離（public / member / admin）は、**Cloud Run のサービス分離と IAM・トークン検証**に置き換える。
境界そのものは残す（第1部 §1.1 の分離理由は移行後も変わらない）。

## 9. 実現性評価（「たぶん動く」で通さない 5 点）

台帳 G-16 で挙げた 5 点の評価結果。**すべて解決済みまたは方針確定済み**で、移行を阻む項目は残っていない。

| # | 論点 | 判定 | 根拠・対応 |
|---|---|---|---|
| 1 | 事務局がスプレッドシートを直接開く運用 | ✅ 解決 | operator 確認で**直接開く運用は無い**と確定。不足していた代替手段（汎用エクスポート・一括編集の対象拡張）は **GAS 側で先に実装済み**（v376.68 / v376.69）。CSV インポートは**現状不要**として見送り（台帳 T-07） |
| 2 | Drive 添付の移行先 | ✅ 方針確定 | **Drive を継続**する。Cloud Storage は東京が無料枠の対象外のため凍結（台帳 T-06 に実単価と試算を保存済み） |
| 3 | Gmail 送信 | ✅ 可能 | サービスアカウントの**ドメイン全体の委任**で代理送信できる。設定にスーパー管理者が 1 回だけ必要。送信上限 2,000 通/日に対し一括 300 通は余裕 |
| 4 | 帳票の PDF 出力 | ✅ 可能・改善 | Cloud Run 上のヘッドレス Chrome に**現在の名簿デザイナが出力する HTML をそのまま**読ませる。レイアウト資産の作り直し不要 |
| 5 | Cloud Run からの下り通信 | ⚠️ 制約あり | 下りの無料枠は北米のみで**東京は対象外**。→ §15 の制約で回避する |

## 10. 認証・権限

| 対象 | 移行後の方式 |
|---|---|
| 管理者 | Google アカウント認証（Firebase Authentication の Google プロバイダ、または Cloud Run 側での ID トークン検証）。**どちらを採るかは未確定**（§19-5）。いずれの場合も**許可リストと権限ロールの判定ロジックは現行をそのまま移す** |
| 会員 | Cloud Run `hcmn-member-auth`。パスワードは Argon2id、pepper は Secret Manager |

**メニュー方式の RBAC**（`ACTION_TO_MENU` → ロールの許可メニュー）は現行の設計をそのまま移す。
判定に GAS 固有機能を使っていないため、そのまま移植できる（`AGENTS.md` §4.8 のゲートを満たす）。

ログイン失敗の時限解除（台帳 T-04）は `ロック解除予定日時` の時刻比較のみで、Firestore のフィールドへそのまま移せる。

## 11. データ設計の移行

### 11.1 マッピング原則

| 現行 | 移行後 | 禁止事項 |
|---|---|---|
| 1 シート | 1 コレクション | — |
| 1 行 | 1 ドキュメント | **行番号を主キーにしない**。既存の `*ID` 列をドキュメント ID にする |
| 削除フラグ | 同名フィールドを維持 | — |
| `*_archive` シート | アーカイブ用コレクション | サロゲート列（アーカイブ ID / 削除バッチ ID / アーカイブ日時）はフィールドとして維持 |
| シート上の数式列 | **アプリ側で計算** | **数式をデータに埋めない**（NG パターン） |
| マスタ（`M_*`） | コレクション | 件数が少ないため起動時に一括読み込みしてよい |

### 11.2 移行時に落とすもの・作るもの

- **落とす**: シートの数式・条件付き書式・入力規則（すべて表示都合であり、業務判定には使っていない）
- **作る**: Firestore の複合インデックス。現行は全件読み込みで済んでいるが、Firestore では**クエリごとにインデックスが要る**

### 11.3 キャッシュ設計

CacheService（1 キー 90 KB・TTL 300 秒・キャッシュミス時は必ず DB から再構築・台帳 T-01）の**設計原則はそのまま移す**。
移行後は Cloud Run のインメモリで代替する。ただし **max-instances=1** の前提が崩れるとインスタンス間で内容がずれるため、
**キャッシュは「消えてもよい」ものに限る**という現行の原則を維持することで担保する。

## 12. メール送信

**単一の出口**（現行の `deliverMail_`）という設計は移行後も維持する。4 段のガード
（全体停止スイッチ／配信方法 LIVE・REDIRECT・SUPPRESS ／転送先の許可リスト／種別ごとの有効無効）と、
未解決のマージタグを除去する処理も**そのまま移す**。いずれも GAS 固有機能に依存しない。

送信手段のみ GmailApp → **Gmail API（ドメイン全体の委任）** に置き換わる。
送信元エイリアスは Gmail に登録済みのアドレスに限られる点は現行と同じ制約。
添付の上限（1 通 20 MB・1 ファイル 10 MB・超過時は送信前に止める・台帳 T-02）も変更しない。

## 13. ファイル添付

**Google Drive を継続する**（台帳 T-06・凍結）。Cloud Run からは Drive API を呼ぶ。
Drive の共有設定に依存した権限制御を**していない**ことは確認済みで、将来 Cloud Storage へ移す余地は残る。

## 14. 帳票 PDF

Cloud Run 上のヘッドレス Chrome で、名簿デザイナが生成する HTML を PDF 化する。

- **API 本体とは別サービスに分ける**。キャッシュを持たないため同時実行を許してよく、`max-instances=1` の制約を掛けない
- 印刷操作が不要になり、余白・ページ割りがブラウザ依存でなくなる（現行からの改善）
- 費用は無料枠内

## 15. 費用設計（¥0 維持の制約）

無料枠の数値は台帳 T-03 が取得元。そこから導かれる**設計上の制約**は次の 5 点で、これは実装時に守る。

1. **静的アセットは Firebase Hosting から配信し、Cloud Run からは返さない**（Cloud Run の下りは東京では無料枠外）
2. **Cloud Run は JSON API のみを返す**（1 応答を数 KB〜数十 KB に抑える）
3. **Firestore は 1 プロジェクト 1 データベース**（検証用に 2 つ目を作ると課金対象）
4. **Cloud Storage を使わない**（東京は無料枠対象外・§13）
5. 既存のガードを維持する: **max-instances=1** ／ **予算アラート 500 円/月** ／ **予算超過の自動停止 killswitch**（実装済み・実イベント受信を実測済み）

現行規模（第1部 §6 の実測値）では Firestore・Cloud Run の計算と保存は無料枠に十分収まる。
**下り通信が唯一の実質的な制約**であり、上記 1・2 がその回避策にあたる。

|---|---|---|

## 17. スキーマ・設定を変えるときの手順

**戻し方が書けない変更はリリースしない。**

| ID | 変更の種類 | 手順 | 検証 | 戻し方 |
|---|---|---|---|---|
| MG-01 | **列の追加・改名・削除** | ①`テーブル定義`/`マスタ定義` を直す ②**`DB_SCHEMA_VERSION` を上げる** ③`docs/er-metadata.json` を更新 ④`npm run build:docs-portal` ⑤push 後に **operator が admin エディタで `runRebuildSchemaForV<版>` を実行**（既存行の列を名前基準でずらす） | `npm run test:er-sync` ／ 再構築関数の戻り値で列の存在を確認 ／ 実行ログに schema-drift の警告が無いこと | 固定 deployment を前版へ redeploy する。**列は残るが空のまま**で旧コードは無視する（破壊的でない） |
| MG-02 | 設定値（システム設定）の追加 | 既定値つきで読み出す実装にする。移行スクリプトは不要 | dryRun で既定値が入ることを確認 | 前版へ redeploy |
| MG-03 | 権限・メニューの追加 | `scripts/menu-registry.mjs` と許可リストの両方を更新 | `npm run test:menu-registry` | 前版へ redeploy |

> **`DB_SCHEMA_VERSION` の更新漏れは、シートが作られず画面が黙って空になる**という形で表面化する
> （v376.65 で実際に発生）。起動時の初期化は版数のキャッシュで飛ばされる経路があるため、
> **列を変えたら必ず再構築関数を明示的に実行する**こと。
