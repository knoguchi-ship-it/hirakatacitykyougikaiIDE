# Release State v351

Date: 2026-05-14
Status: **ROLLED BACK** — admin shell crashed at parse time with `SyntaxError:
Cannot use 'import.meta' outside a module`. All 4 fixed deployments reverted to
v350 (`@309 x2 / @66 / @108`) within minutes of detection. v351 git commits
(`606c520 v351:...`, `f1ed4be docs: v351`, `37d92c5 test: e2e tweak`) are
preserved in history but the artifacts they produced are NOT in production.

## Root cause of rollback

`node_modules/pdfjs-dist/build/pdf.mjs:9421` contains node-only dead code:
```js
const require = process.getBuiltinModule("module").createRequire(import.meta.url);
```
This is inside a `NodeCanvasFactory` method that the browser never invokes,
but `import.meta` is a **syntactic keyword** that only parses inside ES
modules. `vite-plugin-singlefile` rewrites the bundle into a plain
`<script>` tag (without `type="module"`), so the JS engine throws
`SyntaxError` while parsing — admin shell never starts.

User-observed console error:
```
Uncaught (in promise) SyntaxError: Cannot use 'import.meta' outside a module
  at new Function (<anonymous>)
  at userCodeAppPanel?cre…AuthDialog=true:7:3
```

## Lesson

Any npm package whose source contains `import.meta` (even in unreachable
code paths) must be patched / aliased / pre-transformed before being
bundled into a vite-plugin-singlefile artifact. See
`memory/feedback_pdfjs_dist_vite_singlefile_trap.md` for the rule and
mitigation options when retrying.

## Re-attempt plan (v352 候補)

1. `@rollup/plugin-replace` で **`node_modules/pdfjs-dist/**` 内の
   `import.meta.url` を `""` リテラルに置換**してから Vite に bundle させる。
2. もしくは `vite.config.ts` の `resolve.alias` で `pdfjs-dist/build/pdf.mjs`
   を自前 patched 版に差し替え。
3. 採用前: admin index.html を browser で開いて console に SyntaxError が
   出ないことを Playwright で sanity check してから本番 deploy。

## v351 アーキテクチャ

```
[admin が PDF 選択]
  ↓ client (pdfjs-dist v5.7 + Canvas)
1. FileReader → ArrayBuffer (~50ms)
2. pdfjs.getDocument(buf).promise → pdfDoc (~200-500ms)
3. pdfDoc.getPage(1).render(canvas, viewport)   (~500ms-2s)
4. canvas.toDataURL('image/png') → base64 (~50ms)
合計 client side: 1-3 秒
  ↓ 5. PDF + thumbnail PNG (両方 base64) を uploadTrainingFile に POST
  ↓ server (GAS)
6. payload.thumbnailBase64 を Drive に createFile + ANYONE_WITH_LINK
合計: 3-8 秒（PDF サイズ依存）
```

**v350 比較: 20-25 秒 + pending 状態 → 3-8 秒 即完了。**

### Fallback 維持

- client pdfjs render が失敗（暗号化 PDF / 破損 PDF / 古いブラウザ等）→ 例外を
  捕捉して `thumbnailBase64` 無しで upload
- サーバは `thumbnailBase64` が無ければ v350 の `generateAndSaveThumbnailForPdf_`
  経路へ自動 fallback（Drive thumbnailLink polling + 10 分 trigger backfill）
- どの経路でも最終的に thumbnail が生成される設計

## Operator verification

実機で **PDF アップロード時の体感速度** を確認してください:

1. 管理者ポータル → 研修管理 → 新規研修登録 or 既存研修の編集
2. 「ファイルを選択」で **実際の研修案内 PDF**（数 MB）を選ぶ
3. ボタン文言「アップロード中（数秒〜10 秒）...」
4. **5〜10 秒程度** でフォームに 1 ページ目のサムネイル画像が表示される

v350 比で **大幅短縮** が体感できるはずです。もし client 側 rendering が
何らかの理由で失敗した場合は warning が browser console に出て、サーバ
fallback (v350 の 20-25 秒経路) に降ります。最悪でも v350 の挙動は維持されます。
