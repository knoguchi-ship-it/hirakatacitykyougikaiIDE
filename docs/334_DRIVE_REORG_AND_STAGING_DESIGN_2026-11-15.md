## 2. コードから分かった対象と危険（読み取り調査）

| 資産 | ID の置き場 | 注意 |
|---|---|---|
| DB（スプレッドシート） | コードの固定値（`DB_SPREADSHEET_ID_FIXED`・上書きはプロパティ `DB_SPREADSHEET_ID_OVERRIDE`） | 3 プロジェクトとも開く |
| ログ用スプレッドシート | 各プロジェクトのプロパティ `LOG_SPREADSHEET_ID` | プロジェクトごとに値を持つ |
| 外部バックアップ | 名前の接頭辞 `枚方市ケアマネ協議会_DB_Backup`・最新はプロパティ | マイドライブ直下に作られる |
| 研修案内状フォルダ | DB の設定 `TRAINING_FILE_FOLDER_ID` | **中のファイルを「リンクを知っている全員」に公開**（公開ポータルが表示） |
| 請求添付・LINE 投稿資材・一括メール添付 | DB の設定 `*_FOLDER_ID` | LINE 投稿資材も公開リンクを使う |
| ファビコン | プロパティ `FAVICON_*_FILE_ID` | 公開リンク（今の doGet は埋め込みの画像で、ファイルは使っていない） |

**危険**
1. **公開リンク**: 共有ドライブに「組織外と共有しない」「メンバー以外と共有しない」の制限があると、移した時点で公開ポータルの PDF・サムネイルが見えなくなる。→ 棚卸しで共有ドライブの制限（`restrictions.domainUsersOnly`・`driveMembersOnly`）を読み、公開リンクが使えないなら公開しているフォルダは移さない。
2. **新しいファイルの作り先**: フォルダ・バックアップ・宛名リストなどは、コードがマイドライブ直下に作る。移しても新しいものは元の場所に作られ続ける → 第 2 段で「作り先を設定のフォルダにする」改修（ステージングと本番の分離の土台）。
3. 3 つの web アプリは `k.noguchi@hcm-n.org` の権限で動く（R1 で管理者と確認済み）。
4. よい点: Drive の REST 呼び出しはすべて `supportsAllDrives=true`。ファイルの ID は移動で変わらないので、保存した ID はそのまま使える。

## 4. 元に戻す方法（R5・D3 の詳細は D2 で確定）

- **記録**: 移す前に、資産ごとに「ID・名前・元の親フォルダの ID（すべて）・共有設定（アクセスと権限）・移動先」をログ用スプレッドシートの専用シートと、スクリプトプロパティ（最後の 1 回分）に書く。書けなければ移さない。
- **戻し**: `restoreDriveReorg_APPLY` が記録を読み、元の親フォルダへ戻し、共有設定を記録どおりに戻す。資産ごとに結果を出し、失敗したものは手で戻せるよう ID と元の場所をログに出す。
- **戻せることの確認**: 本番の前に、試し用のファイル・フォルダ（公開リンクつき）で「移す → 戻す」を通し、場所と共有設定が元どおりになることを確かめる。
- **移した後の確認**（1 つ移すごと）: `release:verify`（読み取り）、公開ポータルの研修一覧で PDF・サムネイルが表示されること、管理画面のダッシュボード。だめならその資産だけ戻す。
- Drive の画面からも手で戻せる（ID は変わらないので、元の親フォルダへドラッグ）。記録には元の場所の名前も残す。

## 5. D1 棚卸しのツール（本書で実装する分）

`inventoryDriveAssets_LOG()`（管理 split・先頭で `assertMasterOperator_`・引数なし・読むだけ）
- 移動先: `DRIVE_REORG_TARGET_FOLDER_ID_ = '1BKBwQF9dFIwdnEqnpGaeM1iCypSFuPgr'`（秘密ではない）。Drive REST で `driveId`・名前・自分ができること（`capabilities`）、共有ドライブの名前と制限を読む。

- フォルダは中のファイルを数え（上限 2,000 件で打ち切り・打ち切ったことを出す）、公開リンクのファイル数を出す。

## 7. D5 ステージングの設計（2026-11-15・下書き・operator 判断の後に確定）

**目的**: 本番と同じコードを、本番と切り離した環境で先に動かして確かめる（業界の定石の「ステージング」）。今は本番の DB に直接触れて確かめており、書き込みの確認は承認と後片付け（★テストデータの物理削除）が毎回要る。

### 7.1 構成

| 部品 | ステージング | 本番との分け方 |
|---|---|---|
| Apps Script | 新しい 3 プロジェクト（公開・会員・管理）。共有ドライブの `ステージング/` に置く（Apps Script の移動を先にここで試す・R3） | 別のスクリプト ID。`SCRIPT_ID_*` プロパティで doGet の振り分けを合わせる（既存の仕組み） |
| deployment | 各 1 本（本番の「統合・公開 ×2」の旧会員用は作らない） | 別の URL |
| DB | 新しいスプレッドシート（`ステージング/`）。スキーマの整備で表を作り、★＋`@example.invalid` のテストデータだけを入れる（R4） | `DB_SPREADSHEET_ID_OVERRIDE`（既存の仕組み） |
| ログ用スプレッドシート | 新しく作る | `LOG_SPREADSHEET_ID` |
| メール | **送らない**（`MAIL_DELIVERY_STATE=STOPPED`。確かめるときだけ `REDIRECT` で operator の受信箱へ） | DB の設定 |
| パスワードの pepper | ステージング専用の値（本番と別）。**値の設定は operator**（AI は値に触れない・AGENTS L0.1） | スクリプトプロパティ |
| 時間トリガー | 判断待ち（下表） | — |

コードは同じ。環境の違いはすべてスクリプトプロパティと DB の設定で持つ（AGENTS §3 のハードコーディング原則のとおり）。

### 7.2 リリースの流れ（目標）

build → **ステージングへ push → 版 → deployment → 検証（E2E・書き込みを伴う確認）** → 本番へ push → 版 → 4 本 → 検証。
ステージング用の push・版・deployment の記録と hook（H3〜H6）は、本番と別の記録で同じ守りを掛ける（`release:push:staging` を新設・設計の詳細は次の段）。
