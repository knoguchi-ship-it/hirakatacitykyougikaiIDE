## 2. S18 の直し方

`planTableColumnNormalization_` が先に方針を決め、`normalizeTableColumns_` はそれに従う。

| 方針 | 条件 | すること |
|---|---|---|
| same | 定義と同じ | 何もしない |
| append | 今の列が定義の先頭と同じ（末尾に足すだけ） | 見出しのセルを書き足すだけ。行・書式・入力規則・シート ID に触らない |
| rebuild | 並べ替えが要る。消える列は無い | 従来どおり作り直す。**書式を値より先に移す**（書式の無いセルへ文字列を書くと `0123` が 123 になる） |
| blocked | 定義に無い列名・同じ名前の列・見出しの無い列にデータ | **消さずに例外で止める**。critical step なので初期化済みの印も付かない |

末尾の、見出しもデータも無い列は数えない（書式だけの列で getLastColumn が伸びることがある）。

## 3. リハーサル（本番 DB のコピー）

push したコードは、10 分ごとのトリガーがすぐに使う（デプロイの版ではなく最新のコード）。
スキーマの版を上げたまま push すると、確かめる前に本番で整備が走る。そこで順番を分けた。

1. S18 の修正とリハーサルを、**スキーマの版を据え置いて** push（`11246c5` / `af1ddc5`）
2. 管理プロジェクトの HEAD（/dev）から `rehearseSchemaMigrationOnCopy_APPLY` を実行
3. OK を確かめてから版を上げてリリース（`b20accac`）
4. リリース後、整備の済んだ本番 DB のコピーでもう一度実行

ツールの動き: DB をコピー → 定義との差から方針を出す → コピーへ `initializeSchema_` を 2 回 →
全シートの全セルを列名で突き合わせる（値は型付きで比べる。`'0123'` と `123` は別）→
`T_研修申込` に全列の行を 1 行書いて読み戻す → コピーをゴミ箱へ。出力は型と件数だけ（値は出さない）。

| | リリース前（版 v376.71・定義は新） | リリース後（版 v376.125） |
|---|---|---|
| 方針 | T_研修申込 = append（4 列）、T_研修申込_archive = rebuild（空）、T_メール送信ログ = rebuild（※） | T_メール送信ログ = rebuild（※）のみ |
| 1 回目の整備 | 既存データの変化 0。変わったのは T_研修申込・archive だけ | 変化 0 |
| 2 回目の整備 | 変化 0（収束） | 変化 0 |
| 書いて読む | 22 列すべて一致 | 22 列すべて一致 |

※ `T_メール送信ログ` は定義に「研修ID」列があるがシートに無い。起動時の整備の対象外なので今回は何も起きない。
送信ログへの書き込みが列を見出しで引いているかは未確認（記録のみ）。
