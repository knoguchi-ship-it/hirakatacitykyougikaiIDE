## 1. きっかけ

入会申込フロー（個人・賛助・事業所）の**公開前確認**を、コードと実画面の両面で実施した。
その結果、**重大 2 件・中 3 件・軽微 1 件**の不具合が見つかった。

共通する原因は 1 つで、**「同じ判定を別ルートで決めていた」**こと。
入会承認の経路（`createMemberApplicationDirect_`）だけが、他の経路が通っている共通処理を通っていなかった。

## 2. 直した不具合

### 重大 1: ログインIDの重複を検査していなかった

承認経路はログインIDを直書きしていた（個人 `payload.careManagerNumber` / 事業所職員 `cmNumber`）。

退会処理は認証アカウントの**有効フラグを false にするだけで行は残す**ため、ログインIDは占有されたままになる。
一方、重複判定に使う索引は `WITHDRAWN` / `TRANSFERRED` を対象外にする（`isInactiveMemberStatusForIdentity_`）。

→ **退会した会員が同じ介護支援専門員番号で再入会すると、`T_認証アカウント` に同じログインIDが 2 行できる。**
`findRowByColumnValue_` は先頭一致の 1 行しか返さないため、古い無効行に当たって
`アカウントが無効化されています。` となり、**新会員は永久にログインできない**。

**修正**: 管理画面の資格情報発行（`adminIssueMemberCredential_`）と同じ `generateCmBasedLoginId_` に集約した。
同一申込内（事業所の複数職員）での衝突も、払い出すたびに既存一覧へ push して防ぐ。

### 重大 2: 事業所承認の部分書き込み

`createMemberApplicationDirect_` にはロックもロールバックも無く、職員ループの中で
検証と `appendRow` を交互に行っていた。

→ 3 人目で例外が出ると、**会員レコードと 1〜2 人目だけが残る**。申請は `PENDING` のままなので、
事務局が**再度承認するとその事業所がもう 1 件できる**。

**修正**: `LockService` で直列化し、**全職員を検証してから書き込む**順に組み替えた。
スプレッドシートにトランザクションは無いため完全な原子性は得られないが、
落ちる条件（未入力・リスト内重複・カナ不正・人数超過）を先に出し切ることで部分書き込みの窓を最小化した。

### 中 3: 事業所職員のカナだけ正規化されていなかった

職員行の `セイ` / `メイ` / `フリガナ` が入力のまま保存されていた。個人・賛助会員（同じ関数の 100 行上）と、
他の 4 経路（公開の職員追加・会員マイページ・管理画面・一括編集）はすべて正規化していた。

読み取り側の `normalizeStaffNameFields_` は不正文字で**例外を投げ**、それが
**会員一覧を組み立てるループの中で try/catch なしに呼ばれている**。
つまり不正なカナの行が 1 行でも入ると、**管理画面の会員一覧が丸ごと開けなくなる**。

防いでいたのは公開フォームのクライアント検証だけで、**認証不要の公開エンドポイントを直接叩けば作れる**状態だった。

**修正**: `normalizeAndValidateKana_` を通す。あわせて申込時のサーバ側検証（軽微 6）でも弾く。

### 中 4: 賛助会員のログインIDが仕様と違った

仕様（RD BR-01）は「会員番号が無い場合は **9 で始まる 9 桁**」。実装は**会員ID（8 桁数字）をそのまま使用**していた。

介護支援専門員番号も 8 桁数字なので**同じ値空間で衝突しうる**（衝突時は重大 1 と同じ症状）。
確率は低い（現行 222 会員に対し 1 件あたり約 2.2 × 10⁻⁶）が、`会員ID` 自体には重複チェックがあるのに
ログインIDには無い、という非対称は設計の穴だった。

**修正**: 重大 1 と同じ共通関数に集約。専門員番号が無い場合は `generateAutoLoginId_` が `9` ＋ 8 桁を採番する。

### 中 5: 職員数上限が 10 のリテラルだった

新規事業所の `職員数上限` に `10` を直書きしており、システム設定 `DEFAULT_BUSINESS_STAFF_LIMIT` を無視していた。
さらに**申込フォームにも承認処理にも人数チェックが無く**、上限を超える人数で申し込めた。

**修正**: `resolveDefaultBusinessStaffLimit_` を新設して設定値を正本にし、承認時に人数も検証する。

### 軽微 6: 申込時のサーバ側検証が無かった

`enqueueMemberApplicationChangeRequest_` は会員種別と連絡先メールしか見ておらず、
**検証は承認時が初めて**だった。公開エンドポイント（認証不要）としては `AGENTS.md` §6 に反する。

**修正**: `validateMemberApplicationPayload_` を追加。氏名・カナ・専門員番号・メールを申込時に検証する。
重複判定など DB 状態に依存する検査は、従来どおり承認時に行う。

## 3. 仕様変更（operator 決定・2026-09-05）

**公開申込フォームのカナ入力で、ひらがな・半角カナを許可する。**

従来は画面が全角カタカナのみを通し、サーバ（`normalizeAndValidateKana_`）だけが寛容という食い違いがあった。
受理範囲をサーバ側に合わせ、**保存形式は従来どおり全角カタカナ**とする。

- 画面の検証を「**正規化してから判定**」に変更（`normalizeAndValidateKana`）
- **ステップを進めた時点で入力欄の表示も全角カタカナに変わる**。
  送信直前だけ変換すると、利用者は自分の入力した形で確認して別の形で保存されることになるため
- `src/shared/validators.ts` の `KATAKANA_PATTERN` を削除した。
  `src/utils/kanaNormalize.ts` と同じ判定の二重定義で、**公開フォームだけが古い方を見ていた**のが食い違いの原因

## 6. GCP 移植メモ（`AGENTS.md` §4.8.1-5）

- **移行先**: 入会承認は `Cloud Run portal-api` の write action、申込は同 API の匿名 action。
  採番（`generateCmBasedLoginId_`）とカナ正規化は純関数でそのまま移せる。
- **`LockService` → Firestore トランザクション**。今回入れた「検証してから書き込む」構造は、
  トランザクション化するとそのまま原子性が得られるため、**移行で自然に強くなる**。
- **ログインIDの一意性**は、Firestore では `authAccounts` の**ドキュメントIDにログインIDを使う**ことで
  DB 側で保証できる（現在はアプリ側の採番でしか担保していない）。移行時に採用を検討する。
- **未移行 write の増減**: 増減なし（既存 write の内部実装の変更のみ）。
