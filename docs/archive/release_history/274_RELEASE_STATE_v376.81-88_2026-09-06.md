## 1. v376.87 — 規程設定の一括保存が保存されていなかった

v376.86 で入れた一括保存が**本番で 1 件も保存できていなかった**。

`processApiRequest` の `saveRegulationsBatch` 分岐が、この文脈に存在しない `adminSession` を
裸で参照していた。管理者セッションは `parsedPayload.__adminSession` にあり、他の分岐はすべて
そちらを使っている。実行時 `ReferenceError` で保存が丸ごと落ちていた。

```js
- saveRegulationsBatch_(parsedPayload, adminSession && adminSession.loginId)
+ saveRegulationsBatch_(parsedPayload, parsedPayload.__adminSession ? parsedPayload.__adminSession.loginId : '')
```

### なぜ気づけなかったか

**検証用の Playwright スクリプトがエラーアラートを自動承認していた。** 画面は保存完了に見え、
公開ポータル側で並び順が変わっていないことを確かめて初めて分かった。

typecheck は `.gs` を見ず、単体テストは分岐を評価しないため、この層に穴があった。

### 追加した検査: `npm run test:action-dispatch`

`processApiRequest` の分岐を静的に読み、3 点を検査する。

1. 分岐内で `adminSession` を裸参照していないか ← 今回の事故そのもの
2. 分岐が呼ぶ `xxx_()` に定義が実在するか ← 綴り違い・リネーム漏れ
3. `ADMIN_ACTION_PERMISSIONS` にある action に分岐が存在するか ← 登録漏れ

**バグを書き戻すと 1 番が FAIL することを確認済み。**

## 2. v376.88 — 公開ポータルの本人確認を 3 種別へ

### きっかけ

ポータル 3 フローの実地検証中に、**賛助会員が変更・退会のどちらもできない**ことが分かった。
`RD §2` の役割表は賛助会員に「自己情報の更新、退会申請」を認めているので、仕様と実装の食い違いである。

原因は本人確認の鍵。個人は介護支援専門員番号、事業所は事業所番号を鍵にしており、
**賛助会員はどちらも持たない**（入会フォームは個人会員のときしか CM番号欄を出さない）ため、
種別選択から外されていた。

### 実データを数えてから設計した

会員 347 名の登録状況（個人情報は出さず件数のみ。`scripts/diagnose-identity-coverage.mjs`）。

| | 氏名 | カナ | CM番号 | 電話 | 携帯 | メール |
|---|---|---|---|---|---|---|
| 個人会員（187）| 187 | 182 | **167** | 157 | 105 | 69 |
| 事業所職員（159）| 159 | 159 | 155 | — | — | 74 |
| 賛助会員（1）| 1 | 1 | **0** | 0 | 1 | 1 |

**鍵を 1 つに固定すると必ず取りこぼす。** 電話番号に固定すれば個人会員の 30 名が、
CM番号のままなら 20 名と賛助会員全員が弾かれる。メールは 37% しか埋まっておらず鍵にならない。

そこで **「名義 ＋ 手元にある番号を 1 つ」** とした。

| 種別 | 名義 | 選べる番号 |
|---|---|---|
| 個人会員 | 姓・名 | 介護支援専門員番号 / 電話番号 / 携帯電話番号 |
| 事業所会員 | 事業所名 | 事業所番号 / 電話番号 |
| **賛助会員（新規）** | 姓・名 | 電話番号 / 携帯電話番号 |

### 強度は下げていない

- **名義の照合を全種別で必須にした。** 事業所会員はこれまで番号だけで通っていたので**強くなった**
- **番号はちょうど 1 つだけ受け付ける。** 複数欄を同時に開けると、片方が空でも通る抜け道になる
- **登録側が空の項目は一致とみなさない。** 電話番号は 187 名中 30 名が空。空同士を一致にすると、
  氏名を知る者が他人になりすませる
- レート制限（15 分 5 回）は据え置き。鍵が増えた分だけ緩くならないよう、**番号の種類ごとに数える**

### 賛助会員が「事業所会員扱い」になっていた箇所 4 つ

いずれも `memberType === 'INDIVIDUAL' ? 個人 : 事業所` という三項演算子で、
**種別が増えた瞬間に賛助会員が事業所側へ落ちる**書き方だった。

| 箇所 | 症状 |
|---|---|
| 変更申請の allowlist（送信時）| 賛助会員に事業所用の許可リストが適用される |
| 変更申請の allowlist（承認時）| 同上 |
| 画面の項目グループ | 賛助会員に「職員を追加する」欄が出る |
| 入力値の収集判定 | 項目を選んでも入力が拾われず、永久に送信できない |

`PUBLIC_UPDATE_ALLOWLIST_BY_TYPE_` という表引きに寄せ、三項演算子が残っていないことを
テストで固定した。賛助会員の許可リストからは**介護支援専門員番号を外した**
（この番号はログイン ID になるため、持っていない会員に変更経路を与えない）。

### UI の重複を解消

種別選択と本人確認を `src/public-portal/components/IdentityVerifyStep.tsx` に集約した。
変更フォームと退会フォームが同じ内容を別々に持っていたことが、**賛助会員が両方から漏れていた**遠因。
規則と文言の正本は `src/shared/publicIdentity.ts`。

### 実装中に踏んだ罠

**Tailwind の動的クラス名。** `bg-${tone}-50` のように組み立てると v4 のスキャンに引っかからず、
クラスが生成されない（無地の画面になる）。用途ごとに完成形の文字列を持つ表に直した。

## 3. ポータル 3 フローの実地検証（v376.87 時点）

本番に対して、送信 → 管理画面で受理 → 承認/却下 → DB 反映まで実際に通した。

| フロー | 結果 |
|---|---|
| 入会申込（個人）| 注意事項の同意ゲート → 送信 → 承認 → **会員化**（会員番号 81737630）|
| 登録情報変更（事業所）| 送信 → **却下**（理由必須も機能）→ 再送信 → **承認** → 電話番号が DB に反映 |
| 退会申込（事業所）| 送信 → 承認 → `WITHDRAWAL_SCHEDULED` / 退会日 `2027-03-31` → 退会キャンセルで復旧 |

console error は全工程 0 件。**承認するまで `T_会員` は変わらない**ことを確認した。

### 検証で分かった実装の残課題

`SOW §8` に U-27〜U-31 として登録した。**U-27（旧 API 6 本の撤去）が最優先**。

`lookupMemberForPublicUpdate` ほか 5 本が、画面から呼ばれていないのに公開許可リストに残っている。
旧経路は **CM番号 8 桁のみ・試行制限なし・`T_会員` を直接更新（承認なし）** で、
新しい本人確認で固めた守りを迂回できる。呼び出し元は 0 件なので削除できる。

### 検証ハーネス側の失敗（記録として残す）

**1. ダイアログを dismiss していた。** v376.86 の教訓から「自動承認しない」方針にしたところ、
承認ボタンの `confirm()` まで打ち消してしまい、押したのに何も起きない状態になった。
問題だったのは*握りつぶしたこと*ではなく*記録しなかったこと*なので、
**全ダイアログを記録したうえで accept する**方式に改めた。

**2. 「フォームの最初の空欄」に値を入れた。** 変更フォームは全欄が空で始まる（空欄＝変更なし）ため、
電話番号のつもりの値が**事業所名**に入った。承認していれば事業所名が電話番号に化けていた。
却下して作り直し、ラベルで項目を狙い、**入力後に読み返して一致しなければ送信前に落とす**ようにした。

**3. 本人確認のレート制限に当たった。** 同一 ID につき 15 分 5 回。
E2E を連投すると 6 回目から止まるが、症状は `waitForSelector` のタイムアウトなので
セッション切れやセレクタ崩れと区別がつきにくい。
