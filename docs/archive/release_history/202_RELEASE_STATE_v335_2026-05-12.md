# Release State v335 — 2026-05-12

Status: deployed

## Scope

- Public membership applications now create `T_変更申請` rows with `申請種別コード=MEMBER_APPLICATION` and `申請状態コード=PENDING` instead of immediately writing member records.
- Admin approval of `MEMBER_APPLICATION` invokes the existing membership creation path, so credential issuance and duplicate transition logic run only after review.
- Added same-person transition state and audit data:
  - `M_会員状態.TRANSFERRED` / display label `移行済み`
  - `T_会員.移行日`
  - `T_人物統合ログ`
- Same-person key is `介護支援専門員番号`. Blank numbers are not auto-merged.
- Individual/support member → business staff:
  - source member becomes `TRANSFERRED`
  - auth account, admin whitelist link, officer roles, bank account, claims, and training applications move to the new principal
- Member-record duplicate repair:
  - source member becomes `TRANSFERRED`
  - annual fee and payment histories move only when both source and target are member rows, avoiding accidental migration of business-office histories during staff transitions
- Business staff → individual member or another business staff:
  - source staff becomes `LEFT`
  - person-owned records move to the new principal
- Existing member CM duplicate repair now marks old member rows as `TRANSFERRED`, records `移行日`, migrates person-owned records, and writes `T_人物統合ログ`.
