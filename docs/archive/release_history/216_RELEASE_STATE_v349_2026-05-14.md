# Release State v349

Date: 2026-05-14
Status: production deployed

## Scope

案内 PDF サムネイル表示が v272 以来通算 6 度の試行で解決しなかった真因を、Web 検索と
Apps Script Executions の本番ログから完全に突き止め、**「アップロード時にサーバー側で
1 ページ目のサムネイル PNG を Drive 上に永続化し、表示時はその PNG を読み出すだけ」**
の構造へ転換した。

## v272〜v348 が解けなかった本当の理由

- 過去にアップロードされた研修案内 PDF は、当時の OAuth identity (`@uguisunosato.or.jp` 等、
  アカウント移行前) で `DriveApp.createFile` されており、ANYONE_WITH_LINK の link
  経由で **閲覧** はできるが、**現在の deployer (`k.noguchi@hcm-n.org`) は明示的な
  アクセス権を持たない**。
- Drive REST API v3 `files.get` はその不一致を **`404 File not found`** で返す
  （API は権限不足を 403 ではなく 404 で曖昧化する仕様）。これが本番ログで
  `getFileThumbnail_ files.get non-200: code=404` として観測された決定打。
- `DriveApp.getThumbnail()` も PDF に対しほぼ常に null を返す Apps Script の既知制約。
- `drive.google.com/thumbnail?id=...` は Authorization ヘッダー有無に関わらず PDF に
  対して 403 を返す（reCAPTCHA / 別仕様）。
- いずれも **「他人所有の PDF のサムネイルを後追いで取りに行く」** という限界を踏んでいた。

## v349 の解（global standard）

GAS 界 expert Tanaike 氏が 2023 年に公開し以後標準となっている
「pdf-lib + Drive thumbnailLink」パターンを、本案件向けに **1 ページ目だけ** へ簡素化:

```
uploadTrainingFile_(payload):
  1. PDF を Drive に createFile（既存）
  2. Utilities.sleep(3000) → Drive が thumbnail 生成するのを待つ
  3. Drive REST files.get?fields=thumbnailLink (Bearer 付き)
     ※ 自分が今 createFile したばかり = 自分所有 = 200 OK 確実
  4. thumbnailLink (=w800) を Bearer 付きで fetch → PNG bytes
  5. PNG を専用ファイルとして同フォルダに createFile + ANYONE_WITH_LINK
  6. 返却: { url: pdfFileUrl, driveFileId, thumbnailUrl: pngFileUrl }
  (失敗時は thumbnailUrl='' で PDF アップロード自体は成功させる)

getFileThumbnail_(payload):
  - 受け取る URL は事前生成済みの PNG。
  - DriveApp.getFileById(pngId).getBlob() で bytes 取得 → base64 化
  - PNG は自分所有なので 100% 取れる。Drive REST 不要。
  - CacheService 1h TTL、失敗時は SVG プレースホルダ

saveTraining_:
  - 新 URL が旧 URL と異なる場合、旧 PDF / 旧 PNG を trashFileFromUrlIfPossible_
    で trashed（GC）

regenerateAllThumbnails(payload):  // MASTER 一括 backfill (clasp run)
  - 既存研修を走査して同一 pipeline でサムネイル生成
  - 旧 deployer 所有の PDF (現 deployer から不可視) は no_thumbnail_link で
    失敗扱い → ログに研修 ID を残し、admin 側で個別に PDF 再アップロード救済
```

## クライアント変更

- `PdfThumbnail` props 分離: `thumbnailUrl` (PNG / fetch 対象) + `fileUrl` (PDF /
  クリック先)。
- 3 ポータルの呼び出し側 (TrainingApply x2, TrainingManagement, PublicTrainingList)
  を更新。
- admin TrainingManagement のアップロードボタン文言を「アップロード中（サムネイル
  も生成中、10〜15 秒）...」に変更。

## Boundary / Build

- `regenerateAllThumbnails` は **admin プロジェクト top-level callable** として残す
  （clasp run 専用 / processApiRequest からは呼べない）。member / public artifact
  からは build 時 pruning で除去。
- `scripts/audit-admin-boundary.mjs` と `scripts/build-admin-gas.mjs` の allowlist を
  更新。member/public は不変。

## Operator action required (動作確認 2 経路)

### 経路 A: 新規アップロード（一番手っ取り早い検証）

1. 管理者ポータルで研修管理 → 任意の研修を編集 or 新規作成 → 案内 PDF を 1 つ
   アップロード。
2. ボタン文言が「アップロード中（サムネイルも生成中、10〜15 秒）...」となり、
   完了するとフォーム下部に **その PDF の 1 ページ目のサムネイル** が表示される。
3. 研修を保存。
4. 会員マイページの該当研修詳細・公開ポータルの研修一覧でも同じサムネイル画像が
   表示されることを確認。

### 経路 B: 既存研修の backfill（一括）

選択肢 B-1（推奨）: Apps Script editor から MASTER 一括ツールを実行

1. https://script.google.com/u/0/home → admin split プロジェクトを開く。
2. 左ペインで関数選択ドロップダウンから **`regenerateAllThumbnails`** を選択 → 実行。
3. 実行ログに `{ processed, succeeded, skipped, failed: [...] }` が出る。
4. `failed[].reason` が `no_thumbnail_link` のものは **現 deployer から不可視な
   旧 PDF**。該当研修を admin UI で開いて PDF を再アップロードすれば自動で
   thumbnail が付く。
5. 全 webapp はキャッシュクリア済みなので、ブラウザリロードで結果を確認。

選択肢 B-2: clasp run（project-scoped OAuth 要）

```
npx clasp login --creds .tmp/oauth-client-hcmn-member-system-prod.json \
  --use-project-scopes --no-localhost
cd gas/admin
npx clasp run regenerateAllThumbnails --params '[{}]'                  # 全実行
npx clasp run regenerateAllThumbnails --params '[{"dryRun":true}]'     # 件数確認のみ
npx clasp run regenerateAllThumbnails --params '[{"trainingId":"T..."}]'  # 個別
```
