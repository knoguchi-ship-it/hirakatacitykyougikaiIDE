① 設計判断とベストプラクティス適用

Web 検索（2026-05-16 取得）で確認した最新ベストプラクティスを本案件のスプレッドシート DB 上で適用可能な範囲で採用した。

原則採用根拠 / 補足
3NF 正規化（非キー属性は PK のみに依存）採用業務アプリの定石。集計・更新異常を防ぐ
Soft delete（削除フラグ 列）採用既存ルール（docs/03 §7）を踏襲
Audit columns（作成日時 / 更新日時）採用全テーブル統一
Header-Detail パターン（バッチ vs 明細の分離）採用既存 T_支払い / T_支払い明細 と一貫
マスタ参照 FK（enum 直書き回避）採用M_出欠状態 を新設。将来拡張に対応
Polymorphic association 回避（2-FK / 3-FK XOR）採用Sequelize / Hashrocket 2026 推奨。T_研修申込 を 3-FK XOR に移行
命名規約（日本語列名・T_ / M_ プレフィックス）採用案件規約継承
FK enforcement（DB レベル制約）部分採用スプレッドシート DB のため API 層で getMasterCodeSet_ 経由 enforcement
utf8mb4 / charset 統一N/AGAS Spreadsheet は内部 UTF-16 / export 時 UTF-8

② 既存資産流用判断（新規テーブル 3 件却下）

当初計画した新規テーブル 3 件は、既存資産との重複が判明したため新設を却下し、流用設計に切替えた。

✅ 流用判断 #1: ゲスト枠 → T_外部申込者

非会員（電話/紙申込・他体職員参加）の表現に T_研修申込.ゲスト氏名 / ゲスト事業所 列追加を当初計画したが、既に T_外部申込者 テーブルが存在（氏名/フリガナ/メール/電話/事業所名/同意日時）。重複新設を却下し、T_研修申込.外部申込者ID FK 経由で参照する設計に変更。

✅ 流用判断 #2: メール送信ログ → T_メール送信ログ + 新規 T_メール送信明細

メインDB に新規 T_メール送信ログ 作成を当初計画したが、既にログ SS に 同名テーブルが存在（バッチサマリ用：宛先数/成功数/エラー数）。重複新設を却下し、Header-Detail パターンで既存を Header として維持、T_メール送信明細 を per-recipient detail として新設。既存 T_支払い / T_支払い明細 と同一設計パターン。

✅ 流用判断 #3: メールテンプレート → ROSTER_TEMPLATE_LIST

新規 T_メールテンプレート テーブル作成を当初計画したが、既に v316 でテンプレートライブラリ機構が T_システム設定.ROSTER_TEMPLATE_LIST（JSON 配列）として存在。重複新設を却下し、JSON エントリに category: 'TRAINING_REMINDER' | 'TRAINING_THANKS' | 'TRAINING_CANCEL' | 'MAILING_LIST' を追加するのみで流用。既存エントリは欠落時 MAILING_LIST 既定値で auto-migrate（v316 と同パターン）。

結果: v360 で追加するのはマスタ 1 件（M_出欠状態）+ テーブル 1 件（T_メール送信明細）+ 列追加 5 列（T_研修申込: 外部申込者ID, 出欠状態コード, 出欠記録日時, 出欠記録者メール, 事務局メモ）+ 既存 1 列拡張（T_メール送信ログ.研修ID nullable）のみ。

4.1 新規マスタ M_出欠状態

コード名称備考

PRESENT出席

4.3 2-FK XOR 制約（Polymorphic 回避）

🔑 申込者識別の新規約

v360 以降、研修申込者の識別は 3 つの独立した FK 列の XOR 制約を正本とする。

申込者種別会員ID職員ID外部申込者ID
個人会員 / 賛助会員non-emptyemptyempty
事業所職員emptynon-emptyempty
非会員（公開ポータル）emptyemptynon-empty

旧 申込者区分コード / 申込者ID は deprecated。物理列は保持し、新規書込み停止 + 読み取り時の派生のみ。v361 以降で物理削除を計画。

4.4 新規テーブル T_メール送信明細（ログ SS）

既存 T_メール送信ログ（バッチサマリ）の Detail として配置する Header-Detail パターン。受信者単位の送達結果記録。

列名用途
明細IDPK
ログIDFK → T_メール送信ログ
研修IDFK → T_研修 (nullable, 研修関連送信時のみ)
受信者区分MEMBER / STAFF / EXTERNAL
受信者IDポリモーフィック: 会員ID / 職員ID / 外部申込者ID（混在送信先のため不可避）

4.5 既存資産の拡張（テーブル追加なし）

  • T_システム設定.ROSTER_TEMPLATE_LIST JSON: 各エントリに category フィールド追加
  • T_メール送信ログ.送信種別: 新値 TRAINING_BULK を追加（既存値変更なし）
  • T_メール送信ログ.研修ID: nullable で新規列追加（研修関連時のみ populate）

⑥ RDB 整合性検証チェックリスト

  • ✅ 既存テーブルの列削除なし（v360 では物理削除なし、deprecated マーキングのみ）
  • ✅ 既存列の型変更なし
  • ✅ 既存 FK 削除なし
  • ✅ v342 schema-shift guard により末尾列追加は data-shift しない
  • ✅ 既存行の 出欠状態コード 欠落は migration で UNRECORDED 一括設定
  • ✅ 既存 EXTERNAL 行の 外部申込者ID 欠落は migration で 申込者ID から複写
  • ✅ M_出欠状態 マスタ参照は API 層 getMasterCodeSet_ で enforcement
  • ✅ T_メール送信明細 の Header-Detail 削除は論理削除のみ
  • ✅ 事務局メモ は会員境界 audit（audit-member-boundary.mjs）で漏洩検査

セキュリティ境界

  • 事務局メモ 列は管理者専用。fetchAllDataFromDb_ の会員向けフィルタで除外。
  • T_メール送信明細.受信者メール はログ SS に保存され、ログ SS のアクセスは admin split のみ。会員 split から参照不可。
