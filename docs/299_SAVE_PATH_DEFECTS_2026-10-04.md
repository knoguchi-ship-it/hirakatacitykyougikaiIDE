# 保存経路の欠陥 2 件（2026-10-04）

operator 依頼のデータ修正 2 件を `updateMember` で実行したところ、
**依頼した列が変わらず、依頼していない列が変わった。** 原因を追って 2 つの欠陥を直した。

## 1. 事業所番号が書き込まれない — 「成功」と答えて何もしない

```
API : updateMember { id: 36562151, officeNumber: "2772411076" } → success: true
DB  : 事業所番号 "0" のまま
```

| | |
|---|---|
| 管理者 allowlist `ADMIN_MEMBER_WRITABLE_FIELDS_` | `officeNumber` **あり** |
| `saveMemberCore_` の `mergedPayload` | `officeNumber` **無し** |
| `setCol('事業所番号', …)` | **無し**（`getCol` で読むだけ） |

`setCol('事業所番号', …)` が存在するのは `overwritePublicApplicationMemberFields_`
（公開申込の初回登録）だけで、**管理画面からは一度も書けなかった**。

**直し方**: `mergedPayload` に `officeNumber` を載せ、`setCol('事業所番号', …)` を追加。

**再発防止**: `test:validation-matrix` に
「allowlist で許可しているのに保存側が一切参照していない項目が無いこと」を追加した。
同じ型の空振りを allowlist 全体に対して検出する。

## 2. 空の CM 番号にログインIDを書き込んでいた — 値の捏造

```js
// 修正前
var careManagerFallback = storedCareManagerNumber
  || (memberTypeCode === 'INDIVIDUAL' ? loginIdFallback : '');
```

CM 番号が空の個人会員を保存すると、**ログインIDが CM 番号欄へ書き込まれていた**。

### 本番での規模

| | |
|---|---|
| 個人会員 | 181 名中 **19 名が CM 番号 空**（10%） |
| その 19 名の認証アカウント | **全員あり。ログインできる** |
| ログインID | すべて **9 で始まる 9 桁の自動採番**（BR-01 の規定どおり） |
| 事業所職員 | 154 名中 4 名が空 |

**ログインIDは CM 番号ではない。** CM 番号を持たない会員に振られる別物で、
これを CM 番号欄へ入れることは「登録されていない番号」を作り出すことにあたる。
実際、今回の作業で会員 60115713 に `977326986`（＝ログインID・9 桁）が入ってしまった。
個人会員の CM 番号は 8 桁（BR-15）なので、桁数からして CM 番号ではありえない。

**19 名全員が、管理画面での編集 1 回でこの状態になる**ところだった。

### 直し方

```js
var careManagerFallback = storedCareManagerNumber;   // 保存済みの値だけを使う
```

あわせて `validateMemberPayload_` の「賛助会員以外は CM 番号必須」を、
**DB 側が既に空のときだけ**通すようにした（`opts.allowBlankCareManagerNumber`）。
これが無いと、19 名は管理画面から一切編集できなくなる。
新規作成では従来どおり必須（許可フラグを渡すのは `saveMemberCore_` だけ）。

`AGENTS.md` L3.3「既存データを人質にしない」と同じ扱いである。

## 3. operator 提案「ログインIDも振らない」について

> 現在のデフォルト値が空白の場合は、そのまま空白とし、ログインidも振らない建付けで良い。
> ただし、これで問題があるなら教えてほしい。ログインできないのは許容します。

**前半（空白のまま）は実装した。後半（ログインIDを振らない）は実装していない。** 理由:

1. **BR-01 が明示的に認めている仕組みである。**
   「会員番号が無い場合のログイン ID は **9 で始まる 9 桁**を使う」
2. **該当 19 名は全員すでにログインできている。** 振るのをやめても既存アカウントは消えないため、
   この 19 名には何の効果も無い。影響するのは将来の会員だけ。
3. **やめると会員ポータルを使えない会員を新たに作ることになる。**
   現状は使える。機能を減らす変更になる。
4. 変更箇所が**公開ポータルの入会申込を含む 5 経路**に及ぶ。
   本番で最も流量の多い経路で、壊すと新規申込が止まる。

**問題だったのはログインIDの採番ではなく、それが CM 番号欄へ漏れていたことだった。**
漏れを塞げば、採番そのものは残してよい。

> 将来 CM 番号を持たない会員にログインを与えたくない、という運用判断が出た場合は、
> 入会申込の経路を含めた別の改修として扱う。

## 4. 作業中に起きた巻き添え変更（報告済み）

`updateMember` は行全体を読み直して保存し直すため、触っていない列も不変条件へ揃う。

| 会員 | 列 | 変化 | 仕組み |
|---|---|---|---|
| 36562151 | 郵送先区分コード | `OFFICE` → `""` | v131: 事業所会員はブランク強制（BR-05） |
| 36562151 | 携帯電話番号 | `""` → 勤務先電話 | 事業所会員の共有携帯の扱い |
| 60115713 | 介護支援専門員番号 | `""` → `977326986` | **本件の欠陥 2**。修正後は起きない |

前 2 件は設計どおりの正規化で、書き戻しても次の保存で同じになる。
**3 件目だけが欠陥**で、今回直した。

**今後、単一列のデータ修正を `updateMember` で行うときは、
事前に「どの列が巻き添えで変わるか」を提示してから実行する。**
