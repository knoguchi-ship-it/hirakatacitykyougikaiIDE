パスワード Pepper と Secret 管理の比較

Apps Script で会員パスワードを扱うとき、pepper をどこに置くべきかを 「基本情報技術者試験の知識があれば追える」粒度で整理した資料です。 2026-04-30 時点の公式情報と OWASP / NIST の考え方に基づきます。

対象: 会員 loginId + password 方法2: Script Properties 方法1: Secret Manager / 外部KDF
目次 1. 先に結論 2. 用語整理 3. 方法2: Script Properties 4. 方法1: Secret Manager / 外部KDF 5. 比較表 6. 2 から 1 への移行 7. 本番運用手順 8. 推奨判断 9. 参照情報

1. 先に結論

pepper の値は、ソースコードに直書きしません。Git、DB、HTML、handover、チャット、ログにも残しません。 コードに書いてよいのは PASSWORD_HASH_PEPPER_V1 という設定名だけです。

この案件の現実解: まず方法2の Apps Script Script Properties に pepper を置く。 将来、方法1の Google Cloud Secret Manager、さらに必要なら外部 KDF / managed identity へ移行する。
判断 内容
禁止 pepper の値をソースコード、Git、DB、docs、ログ、チャットへ書く。
短期の現実解 Apps Script の Script Properties に PASSWORD_HASH_PEPPER_V1 として保存する。
長期の理想形 Secret Manager で IAM、監査、バージョン、ローテーションを管理する。さらに認証基盤を外部 KDF / managed identity へ移す。

2. 用語整理

salt

ユーザーごとの公開前提の乱数

同じパスワードでも、ユーザーごとに異なる hash になるように混ぜる値です。 salt は password hash と一緒に DB へ保存してよい値です。

pepper

システム側だけが知る秘密の乱数

DB が漏えいしても、pepper が別管理されていれば攻撃者は hash の検証が難しくなります。 pepper は DB にもコードにも置きません。

KDF

パスワードから検証子を作る処理

PBKDF2、bcrypt、scrypt、Argon2id などです。計算をあえて重くして、 パスワード総当たり攻撃のコストを上げます。

secret store

秘密情報を置く専用の保管場所

API key、token、pepper などを管理する場所です。 良い secret store はアクセス権限、監査、ローテーションを持ちます。

3. 方法2: Apps Script Script Properties

Apps Script 標準の PropertiesService.getScriptProperties() を使う方法です。 Google 公式ドキュメントでは、Script Properties はスクリプト単位の key-value 保存場所と説明されています。 ただし properties は別 script と共有されないため、この案件では 3 つの Apps Script project それぞれに同じ値を設定します。

1

強乱数で pepper を 1 つ生成する

生成した値は誰にも貼らず、作業ログにも残しません。

2

3 project の Script Properties に同じ値を設定する

integrated/public、member split、admin split に PASSWORD_HASH_PEPPER_V1 を設定します。

3

コードは設定名だけを読む

値はコードに出ません。property が未設定なら認証を失敗させます。

function getPasswordPepper_() {
  const value = PropertiesService
    .getScriptProperties()
    .getProperty('PASSWORD_HASH_PEPPER_V1');

  if (!value) {
    throw new Error('Password pepper is not configured.');
  }
  return value;
}
注意: Script Properties は Secret Manager より軽量ですが、IAM による細かい secret 単位の制御、secret version 管理、標準的なローテーション運用は弱いです。 短期の実用解として使い、長期的には Secret Manager 化を検討します。

4. 方法1: Secret Manager / 外部 KDF

方法1は、より強い本番運用を目指す構成です。段階が 2 つあります。 まず pepper を Google Cloud Secret Manager へ移し、さらに必要なら password hash の計算自体を外部 KDF / managed identity に移します。

1-A

Secret Manager に pepper を置く

Secret Manager は secret data を version として保存し、IAM でアクセス制御できます。 監査、ローテーション、ロールバック設計がしやすくなります。

1-B

外部 KDF / managed identity に移す

Apps Script 内の PBKDF2 ではなく、Argon2id や scrypt などを使える認証専用コンポーネントへ移す考え方です。 セキュリティは上がりますが、設計範囲は大きくなります。

段階 主な変更 難易度
1-A: Secret Manager 化 pepper の保存先を Script Properties から Secret Manager に変更する。 小から中
1-B: 外部 KDF 化 パスワード検証ロジック、レート制限、監査、障害対応まで含めて認証基盤を再設計する。 中から大

ソースコード直書き回避 可能。 可能。
権限管理 script project 単位。細かい secret 単位の IAM は弱い。 IAM、secret 単位の権限、環境分離を設計しやすい。

6. 2 から 1 への移行イメージ

重要なのは、pepper の値を変えず、保存場所だけを変えることです。 そうすれば既存 DB の password verifier は壊れません。

1

今: Script Properties から読む

getPasswordPepper_() の中で PropertiesService を使います。

2

移行準備: provider を分ける

getPasswordPepper_() はそのままにし、内部だけ ScriptProperties provider と SecretManager provider に分けます。

3

移行期間: Secret Manager 優先、Script Properties fallback

短期間だけ fallback を許可します。値は同一である必要があります。

4

移行完了: fallback を削除

Secret Manager だけを正本にします。Script Properties の古い値は撤去します。

// 移行しやすい形の例
function getPasswordPepper_() {
  return getPasswordPepperFromScriptProperties_();
}

// 将来の切り替え例
function getPasswordPepper_() {
  return getPasswordPepperFromSecretManager_();
}
移行内容 工数目安 DB 影響
Script Properties から Secret Manager へ保存先だけ変更 2から5人日 原則なし。pepper 値を変えないため。
外部 KDF / managed identity へ認証基盤を移行 2から4週間 あり。verifier 形式、移行状態、ログイン成功時 rehash などの設計が必要。

7. 本番運用手順

絶対禁止: pepper の値をコード、Git、DB、HTML、docs、handover、ログ、チャットへ書かない。 作業証跡には「設定済み」とだけ残します。
  1. 強乱数で pepper を生成する。
  2. integrated/public project の Script Properties に PASSWORD_HASH_PEPPER_V1 を設定する。
  3. member split project の Script Properties に同じ値を設定する。
  4. admin split project の Script Properties に同じ値を設定する。
  5. 値を表示せず、3 project すべてで「設定済み」であることだけ確認する。
  6. 未設定が 1 つでもあれば release を止める。
  7. 本番反映後、ログイン、パスワード変更、初期パスワード発行、再発行を確認する。

property がない場合は認証を通す fallback を作らず、fail closed にします。 これは「設定ミスを早く検出する」ためです。

8. 推奨判断

今回採用する方法

方法2の Script Properties を採用します。理由は、Apps Script と相性がよく、 コード直書きや DB 保存を避けられ、短期の本番投入に必要な安全性を確保できるためです。

将来の改善先

方法1の Secret Manager 化を次フェーズの候補にします。 さらに高い password storage 水準を求める場合は、外部 KDF / managed identity を設計します。

設計上の固定点: getPasswordPepper_() に取得処理を集約しておけば、保存先を Script Properties から Secret Manager へ変えても、ログイン画面や DB schema への影響を小さくできます。
