3. 名簿出力 Visual Designer（v372 S1〜S1.6.1）

3.1 背景・設計

旧 RosterExport.tsx は外部 Google Sheets テンプレ依存で柔軟性・カスタマイズ性が低く「ほぼ使えない」状態だった。設計書 docs/228 に基づき 5 Sprint で全面刷新。Sprint S1.6.1 まで本番反映済み。

3.2 アーキテクチャ

  • バックエンド: getRosterFieldDictionary_（40 フィールド宣言）/ getRosterDesignerData_（生データ Record 返却）/ saveRosterTemplateV2_ 等の admin callable
  • 保存先: T_システム設定.ROSTER_TEMPLATE_LIBRARY_V2（JSON 配列）
  • フロント: src/components/RosterDesigner.tsx — Tab 式 2 ステップ（設計 / プレビュー&出力）
  • フィールドグループ 7 種: auto / member / individual / office / staff / fee / computed
  • 統合フィールド: autoName / autoKana / autoEmail / autoCareManagerNumber — 出力単位（MEMBER/STAFF/MIXED）に応じて自動的に適切な値を返す

3.3 出力単位 3 択

  • 会員単位（既定）: 個人/賛助/事業所 各 1 行
  • 事業所職員単位: 事業所職員 1 名ごと 1 行
  • 混合: 個人/賛助 + 事業所職員

3.4 行フィルタ（rowFilter）

各列に演算子 + 値 + 否定トグルを設定可能。全列 AND 評価。

型演算子セット
string含む / 等しい / 始まる / 終わる / 空 / 空でない
number= / > / < / ≥ / ≤ / 範囲 / 空 / 空でない
date等しい / 以前 / 以降 / 期間 / 空 / 空でない
enumいずれか / 空 / 空でない

否定トグル: Linear 流の is / is not パターン。含む + NOT = 含まない。

4. 介護支援専門員番号 admin 例外（v372.4）

4.1 バリデーション規約

場面ルール
公開ポータル全般厳格: 8 桁半角数字 /^\d{8}$/
会員マイページ厳格: 8 桁半角数字
admin 会員詳細編集 MemberDetailAdmin緩和: 8 桁数字 または 1〜10 桁半角英数字

4.2 例外パターン

  • 看護師・保健師等: HN + 事業所番号下 8 桁 → 例: HN12345678
  • 社会福祉士: HS + 事業所番号下 8 桁 → 例: HS12345678

4.3 セキュリティ

  • MASTER / ADMIN 権限のみ緩和許可（isAllowedRelaxedCmNumber_）
  • 二重防御: ADMIN_ACTION_PERMISSIONS で updateMember / updateStaff 自体が MASTER/ADMIN 限定
  • DB 保存時に大文字化（normalizeCmNumberForStorage_）
  • 重複チェックも大文字統一（normalizeCmNumberForKey_）

5. 公開ポータル 職員情報変更（v372.5）

5.1 概要

会員マイページに入らずに、公開ポータルから事業所代表者が 既存職員の情報を変更申請 できる機能。

5.2 フロー

  1. 「会員登録情報を変更する」→ 事業所会員 → 事業所番号で本人確認（HMAC token 発行）
  2. 「変更項目の選択」で 「職員情報を変更する」 にチェック
  3. 「変更内容の入力」で在籍職員カード一覧表示
  4. 各カードで「変更する」チェック + 変更したいフィールドのみ入力（空欄=変更なし）
  5. 送信 → T_変更申請 に PENDING 保存
  6. 管理者承認 → updateStaff_ で反映 + メール変更時は旧・新両方に通知

5.3 セキュリティガード

  • 所属検証: 申請の memberId と職員の所属 memberId が一致するか確認
  • 10 桁等の admin 緩和 CM 番号は 公開ポータルで編集不可（disable + 管理者連絡案内）
  • CM 番号変更時の警告: 「ログイン ID が変わる」「新 CM でログイン」

5.4 申請内容 JSON 拡張

{
  "fields": { "officeName": "...", ... },
  "staffAdd": [...],
  "staffRemove": [...],
  "staffUpdate": [
    {
      "staffId": "...",
      "lastName": "...",  // 変更したいフィールドのみ含む（空欄=変更なし）
      "email": "..."
    }
  ]
}

6. バグ修正 + デザイン整合性（v372.6 / v372.6.1）

6.1 不具合 1: 申請者表示名が ??? 化

原因: Utilities.base64EncodeWebSafe() / computeHmacSha256Signature() に charset 未指定で日本語が ISO-8859-1 解釈となり ? 置換。

修正: Utilities.Charset.UTF_8 を encode/verify 両側で明示。

副作用: 既存トークン無効化（30 分以内に再認証で OK）。

6.2 不具合 2: 全空欄でも申請送信可能

  • バックエンド submitPublicChangeRequest_: 全空チェック → エラー返却
  • フロント MemberUpdateForm.tsx: useMemo で hasAnyInput 計算 → 送信ボタン disable + ヒント表示

6.3 デザイン整合性

  • AddressInput の必須マーク * 削除 → 「空欄=変更なし」モデル統一
  • 「新しい情報を入力」上部に強調ガイダンスバナー（violet-50 + 📝 + 箇条書き）
  • プレースホルダー「例:」プレフィックス統一
  • 送信ボタン disable + aria-disabled + title ツールチップ + インラインヒント

6.4 cleanup 関数

7. メール送信 4 階層ガード（v371.x 継続）

⚠️ 現在 safe-stop 状態: MAIL_GLOBAL_ENABLED=false で起動。テスト時は REDIRECT モードに切替。詳細は docs/227。

7.1 4 階層

  1. MAIL_GLOBAL_ENABLED — 全停止スイッチ
  2. MAIL_DELIVERY_MODE — LIVE / REDIRECT / SUPPRESS
  3. MAIL_REDIRECT_ALLOWLIST — REDIRECT 時の宛先（CSV）
  4. カテゴリ別 ENABLED — 既存 9 + 補完 6 = 15 カテゴリ

7.2 全メール送信箇所が deliverMail_ 経由

v371.2 で 18 箇所の MailApp.sendEmail / GmailApp.sendEmail / sendEmailWithValidatedFrom_ 直呼出しを deliverMail_(category, to, subject, body, options) に統一。
