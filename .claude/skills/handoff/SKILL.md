# 引き継ぎ（ハンドオフ）

**次の担当者は、この会話を読まない。** 読むのは `AGENTS.md` → `HANDOVER.md` §0.0 だけだと考えて書く。

## 1. HANDOVER.md §0.0 を書き直す

| 書くこと | 例 |
|---|---|
| 日付と「どういう状態で閉じたか」 | コード・文書・本番が整合している／未リリースの変更がある |
| 本番の版（4 本）とロールバック先 | 書いたら `npm run release:verify` で本番と照合する |
| このセッションでやったことの要約 | 版ごと 1〜2 行。詳細は `docs/release-notes-2026.md` へ |
| 残っている作業の表 | **誰が**（AI / operator）・何を待っているか |
| 未解明・未検証 | 「未検証」と明記する。黙って埋めない |

古い §0.0 の内容は消してよい（履歴は release-notes と git にある）。HANDOVER は**現状だけ**を書く。

## 1.5 レビュー（必須・hook が強制する）

**ハンドオフの指示があると、レビューが通るまで返答を終えられない**（hook H9・2026-11-01 operator 指示）。
発火条件（2026-11-14）: `/handoff`・`$handoff`、または独立した行の明確な引き継ぎ依頼。引用・コードブロック・否定・条件付きの言及・説明の質問では発火しない。複雑な依頼は明示コマンドを使う。レビュー後に未コミット差分・未追跡ファイルが生じた場合は、そのHEADでも再確認する。印はセッションごとに保存し、別セッションの印は削除・上書きしない。コードブロックは開始記号の種類・個数に対応する終了行まで除外する。旧形式の単一ファイルも読めるようにする。
レビューは「判断の項目（ここ）」と「機械の項目（`npm run handoff:review`）」の 2 つ。順に行う。

### 判断の項目（AI が読んで確かめる）

前回のハンドオフ（HANDOVER の前の §0.0）以降の変更すべてについて:

| 確かめること | 見る場所・やり方 |
|---|---|
| **仕様書に旧い記述・書き漏れが無い** | 変更した動きの言葉で `docs/spec/` を全部引く（手順は Skill `/spec-sync`）。`Spec: 不要` としたコミットも理由が今も正しいか見直す |
| **実装が operator の決定・規定と合っている** | 決定の記録（`docs/3xx` の operator 決定表・MEMORY）と実装を 1 件ずつ突き合わせる。設計レベルの食い違いはその場で直さず、報告と HANDOVER に載せる |
| **未検証を完了に混ぜていない** | 「本番で確かめた」「ローカルの検査だけ」「未実施」を書き分ける。テストが通っただけのものを完了と書かない |
| **文書どうしが食い違っていない** | HANDOVER・release-state・release-notes・`docs/09`・計画書（`docs/3xx`）の版・状態・残作業 |
| **operator にお願いすることが漏れていない** | 承認待ち・ログイン・判断待ちを「誰が・何を」で表にする |

見つけたものは直す（設計レベルは直さず報告）。直したらコミットする（機能のコードを含むなら `Spec:` 行）。

### 機械の項目（最後に必ず通す）

```bash
npm run handoff:review   # 作業ツリーがきれい・Spec 行の漏れなし・HANDOVER の冒頭に今日の日付と「未検証」の欄
```

通ったときだけ、この HEAD でのレビュー済みの記録が残り、hook が返答を終えることを許す。
**記録はスクリプトしか書けない**（AI が自分で「済み」と書かない）。通った後にコミットしたら、もう一度通す。
どうしても通せない理由（operator の操作待ちなど）があるときは、理由を報告する。hook は 2 回戻した後は止まり、判断を operator に渡す。

## 2. 決まったルールの置き場所を決める

この会話で operator が決めたこと・踏んだ事故を 1 つずつ、**守らせ方の強い順に**置き場所を選ぶ。

| 置き場所 | 向いているもの | 例 |
|---|---|---|
| **hook**（`.claude/hooks/`） | AI の操作そのものを止める・確認を出す | `clasp deploy` 拒否・書き込み関数の確認 |
| **npm 検査**（`prerelease` に連結） | コードの形で判定できる | 監査ログの出口が 1 つ・保守ツールの先頭で実行者確認 |
| **Skill**（`.claude/skills/`） | 手順。作業のときだけ読めばよい | リリース・本番 DB・管理ツールの追加 |
| **AGENTS.md** | 常に頭にあるべき原則（短く） | 破壊的な修正は着手前に声を掛ける |
| **MEMORY** | operator の好み・判断の背景 | ユーザビリティを後回しにしない |

- **機械で判定できるものを文章だけで済ませない。** 検査を足したら、**直す前のコードで落ちる**ことを確かめる
  （通るだけのテストは何も守っていない）。
- hook は `npm run test:guards`、Skill は `npm run test:skills` が中身を検査する。足したら両方を通す。
- 新しい Skill は **AGENTS.md L4.2 の表へ足す**（`test:skills` が照合する）。読み込まれるのは次のセッションから。
- AGENTS.md の L2 表（機械が守る規約）に、足した検査を 1 行で載せる。

## 3. 最終確認

```bash
npm run prerelease        # exit 0
npm run release:verify    # 本番 4 本と HANDOVER の一致（clasp の認証が要る）
git status --short        # 未追跡ファイルを残さない
```

コミットして push する（`git push` は prerelease 通過済みの HEAD でないと hook が拒否する）。

## 4. 報告

operator への最後の報告には、**やったこと・残っていること・operator にお願いすること**を分けて書く。
未検証のもの・承認待ちのものを、完了したものに混ぜない。
