# 仕様書の追従確認

**旧い記述が残ると、次の担当者が仕様を誤認する**（2026-11-01 operator 指示）。
実例: 会員移行の「処理待ちの申請で止める」（v376.139）と「最後の在籍職員の移行ガード」（v376.140）が、
設計書（`docs/316`）とリリース記録には書かれたのに、要件定義（`docs/spec/02_RD.md` §2 の 4）は古いままだった。

**起動条件は機械が見る**: 機能のコードを含むコミットに `Spec:` 行が無いと、hook（`guard-bash` H8）が止める。
リリース前は `npm run test:spec-trailer`（`prerelease` の一部）が、基点以降の全コミットを確かめる。
**この手順書は「何を確かめて、どう直すか」を書く。** 判定の正本は `scripts/spec-trailer.mjs`。

## 手順

### 1. 今回の変更を把握する

```bash
git diff --cached --stat
git diff --cached -- gas-src src
```

「動き（何が受け付けられ、何が止まり、誰が何をできるか）が変わったか」で分ける。
内部の整理だけ（関数の分割・名前・性能）なら、手順 4 の「不要」へ。

### 2. どの仕様書に関わるかを引く

| 変わったもの | 確かめる場所 |
|---|---|
| 業務ルール・判定・止める条件・例外の扱い | `02_RD.md`（§2 の例外表・UC・BR 一覧） |
| 権限・誰が何をできるか | `02_RD.md` の役割表、`docs/246`（RBAC） |
| 画面・文言・遷移・表示の条件 | `04_UIUX.md` |
| 表・列・API の action・データの形 | `05_DATA_IF.md`（ER は `/doc` の手順で自動生成） |
| 技術の制約・構成・送信方式 | `03_TRD.md` |
| 範囲・やらないこと | `01_SOW.md` |

### 3. 旧い記述を探して直す

- **キーワードで docs/spec を全部引く。** 変えた動きの言葉（例: 「移行」「退会」「受付」「締切」）と、
  関数・列・コードの名前の両方で探す。**見つかった箇所はすべて読む**（1 か所直して終わりにしない）。
  ```bash
  grep -n "移行\|退会" docs/spec/*.md
  ```
- **今の動きと食い違う記述を直す。** 書き漏れ（新しい止め方・例外）も足す。
- **業務ルールを足す・変えるときは `/spec-change` の手順で行う**（BR 番号・`test:validation-matrix`・`docs/268`・改訂履歴）。
  この Skill は「確かめる」入口、BR の登録手順の正本は `/spec-change`。
- **まだ実装していない決定は、仕様書に「今の動き」として書かない。** 計画書（`docs/3xx`）に置き、仕様書には書かない。
- 文書の書き方（文字コード・索引）は `/doc` に従う。
- 実装と仕様書の**どちらが正しいか分からない**ときは、勝手に寄せず operator に確認する。

### 4. 結果を Spec 行に書く

コミットメッセージに 1 行（行頭に `Spec:`）。

| 場合 | 書き方 |
|---|---|
| 仕様書を直した | `Spec: docs/spec/02_RD.md §2-4・BR-22 を追加` （docs/spec/ のパスを必ず含める） |
| 直さなくてよい | `Spec: 不要（画面の文言だけで仕様書に記載なし）` （理由を（）に。理由は「確かめた結果」を書く） |

- 仕様書の修正は**同じコミットに含める**のが基本。分けるなら、先に仕様書のコミットを作る。
- **「不要」は確かめた後にだけ書く。** 手順 3 の検索をせずに「不要」と書くのは、この仕組みの抜け道になる。
- `Spec:` 行の無いコミットが既にある（Codex など hook の外で作られた）ときは、
  後のコミットに `Spec-For: <短縮ハッシュ> docs/spec/… を直した` か `Spec-For: <短縮ハッシュ> 不要（理由）` を書いて補う。

## 完了条件

```bash
npm run test:spec-trailer        # 基点以降のコミットすべてに Spec 行がある
npm run test:docs-single-source  # BR を足したときのトレーサビリティ
```
