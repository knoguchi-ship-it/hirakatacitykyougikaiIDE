# 本番 DB を触るときの手順

**テストのときだけの話ではない。** operator 依頼の 1 セル修正も、同じ手順を通す。

## なぜ要るか — 2026-10-04 と 10-08 に踏んだ 2 つ

```
① updateMember を単一列の更新に使った
     → 狙った列（事業所番号）は変わらず、別の 3 列が変わった
② dryRunApplicationScenarios を「名前からして非破壊」と思い込んで実行した
     → 本番に会員行と認証アカウントができた
```

**どちらも、事前に 1 ステップ踏んでいれば防げた。**

## 手順

### 1. 書き込みの有無をコードで確かめる

**名前を信用しない。** `dryRun` も `preview` も、書き込まない保証ではない。

```bash
grep -n "appendRow\|setValues\|setCol\|appendRowsByHeaders_" <該当関数の範囲>
```

`dryRunApplicationScenarios` は**本番 DB に会員・認証アカウントを作る**。
`previewDeleteMember` は読むだけ。この違いは名前からは分からない。

### 2. 影響範囲を先に提示する

**「どの列が巻き添えで変わるか」を実行前に出す。**

`updateMember` / `saveMemberCore_` は**行全体を読み直して保存し直す**ため、
payload に無い列も不変条件に合わせて書き換わる。既知のものだけでこれだけある。

| 条件 | 起きること |
|---|---|
| 事業所会員を保存 | 姓・名・セイ・メイ・CM番号・発送方法・郵送先区分が**ブランク強制**（v131） |
| 事業所会員で携帯が空 | 勤務先電話が**携帯へ転記**される |
| 勤務先名が `勤務なし` | 勤務先の電話・FAX・住所が**消える**（2026-10-04 で意図的に追加） |

### 3. operator の承認を取る

対象・件数・不可逆性を明示する（MEMORY L0）。
**プレビューがある操作は、プレビュー結果を見せてから承認を求める。**

### 4. 変更前のスナップショットを取る

**全列**。差分を出すのに要る。
設定を変える場合は `getSystemSettings` の全キー（`updateSystemSettings` は
**部分更新できない**ので、read-modify-write の元としても要る）。

### 5. 実行する

### 6. 全列差分で確認する

**「意図した列だけが変わり、巻き添えが 0 であること」を数字で示す。**

```
変わった列 2 / 全 35 列
  事業所番号: "0" → "2772411076"
  更新日時
```

「成功しました」では足りない。**API が success を返しても列が変わらないことがある**
（`updateMember` の事業所番号がまさにそれだった）。

### 7. 後片付けは実数で確認する

**preview の申告を信用しない。**

```
previewDryRunApplicationCleanup の申告   members: 0
実際                                      会員 1 件が残存
```

件数を自分で数える。基準値（会員 218 / 職員 156 など）と突き合わせる。

### 8. 削除は論理削除で、バッチ ID を記録する

```
previewDeleteMember → 対象と件数を確認
executeDeleteMember（confirmText: '論理削除'）
→ logId / batchId を記録する。復元は restoreLastArchiveBatch_APPLY
```

## メールを伴う検証

**カテゴリ別フラグを切るだけでは足りない。** 受付通知・承認通知・資格情報メールなど
他の経路が動く。`deliverMail_` が全メールの唯一の出口なので、**全体を止める**。

```
検証前  getSystemSettings で全キーを控える
検証中  mailDeliveryState = 'STOPPED'（read-modify-write で保存）
        → mailGlobalEnabled も false へ自動同期される
検証後  mailDeliveryState = 'LIVE' へ復元し、変わった設定が 2 キーだけであることを確認
証跡    T_メール送信ログ に当日の行が無いことを確認する
```

**第三者（実在の事業所・会員）へメールが飛ぶ可能性があるときは、必ず止めてから行う。**

## テストデータを作る場合

- メールは `@example.invalid`（RFC 6761 の予約ドメイン。外部へ届かない）
- CM 番号は**使用済みを全件集めてから**未使用を選ぶ（削除済みの行も含める）
- 対象事業所は**影響の小さいところ**を選び、**実行前に会員 ID と名称を提示する**
- 終わったら論理削除し、**実数が元に戻ったことを確認する**

> 実アドレスを使うテスト会員は、自動 cleanup（`.invalid` 完全一致）の対象外になる。
> 作ったら手で片付ける（`feedback-live-mail-test-member`）。

## Hook との関係

破壊的な `clasp run`（`seedDemoData` / `deleteTestData_APPLY` など）は
PreToolUse hook が `ask` を出す。**手順を飛ばしても最後の砦が残る。**
ただし**管理画面経由（`google.script.run`）は Bash を通らないので止まらない。**
そちらはこの手順で担保する。
