システム設定の差分保存と
clasp run 切り分け設計

Windows のコマンド行上限により、約31KBの設定JSONを clasp run --params で渡せない問題を、差分保存と機能群別・無書込みの診断JSONで解消する設計です。

未リリースprerelease完走待ち ローカル対象テストとGAS生成物は復旧済みですが、現在の作業ツリーをリリース可能と宣言するものではありません。

1. 目的と適用範囲

目的設計上の回答
保存JSONを小さくする管理画面は読込み時の基準値と比較し、変更されたキーだけを送る。
保存前に全体の妥当性を保つサーバーは未送信キーを現在値として補い、同じ検証経路で全項目を確認する。ただし未送信キーは書き込まない。
Windows由来の失敗を切り分ける設定値を含まない小さなJSONを、core / publicPortal / mail / chat ごとに実行する。
誤って本番を書き換えない診断actionはdry-run固定で、書込み数 0 以外を失敗とする。

範囲外: 楽観ロック、設定の履歴化、設定値を外部へ出す診断、通常リリース時の本番書込みテスト。これらは本設計では導入しません。

2.1 クライアントの契約

  • 設定取得直後の値を基準値として保持する。
  • 「設定を保存」時、候補値と基準値の差分だけを送信する。
  • 保存成功時だけ、サーバーから返った設定値を新しい基準値に置き換える。
  • 同じキーを二人が編集した場合は後から保存した値が残る。異なるキーなら、互いの未変更値は上書きしない。

2.2 サーバーの契約

  • 送信されたキーだけを更新候補へ入れる。
  • 送信されなかったキーはDBの現在値で検証するが、更新候補へは入れない。
  • すべての入力・参照・権限を検証してから、ロックの中で一括保存する。
  • 検証不能、空欄禁止、存在しない定型文IDなどは理由を示して拒否し、保存はゼロ件とする。
メール件名・本文を含む必須項目は、保存時・読取り時・送信時のいずれでも既定文面で補いません。初期データ投入時だけ既定文面を使い、以後は空欄をfail-closedで止めます。

3. 診断actionの設計

管理者専用action checkSystemSettingsPatch を追加します。権限は MASTER / ADMIN とし、通常の設定保存と同じ検証関数を __dryRun: true で通します。

入力（fixtureが渡す値）
{ "suite": "mail" }

成功時の返却（設定値・本文・送信元は返さない）
{ "suite": "mail", "valid": true,
  "checkedFieldCount": 45, "plannedSettingCount": 0,
  "plannedMemberFeeCodeCount": 0, "writes": 0 }
suite検証対象JSONファイル
core基本設定、年会費、フォルダ、研修履歴などtest-fixtures/clasp-system-settings/core.json
publicPortal公開ポータルの表示設定、入会完了画面設定など…/public-portal.json
mailメール有効状態、件名・本文、送信制御など…/mail.json
chatGoogle Chat通知の有効状態と本文…/chat.json

fixtureには機能群名・期待する valid と writes: 0 だけを書き、設定値・メール本文・送信元・認証情報を置かない。

4. 使う条件と判断フロー

通常のリリース前検査には含めない。 fixtureは、ローカルで再現できない実行経路を小さく切り分けるための運用診断であり、全設定保存の代替テストではありません。
  1. 変更に対応するローカルテスト（例: test:screen-text-templates、test:mailrender）と生成物同期テストを先に成功させる。失敗している間はfixtureを実行しない。
  2. 全設定JSONを渡す通常の clasp run 確認が、Windowsの引数長・JSON引用符崩れ・Execution API経路で失敗または実行不能になった場合に限り、fixtureを使う。
  3. npm run test:clasp-settings-fixtures を実行する。特定群だけなら末尾に mail 等を指定する。
  4. 全群成功なら「アプリ側検証は通り、巨大JSONのWindows運搬だけが問題」と判定する。設定値は変更しない。
  5. 一群でも失敗なら、その群のサーバー検証・認可・Execution APIを調査する。失敗を回避するために設定値やfixtureを大きくしない。
状態判定次の行動
ローカルテスト失敗（JSONサイズ以外）実装またはテストが未完成先にローカル失敗を直す。修正後は承認済みリリース後の本番検証まで必須。
ローカル成功、巨大JSONだけ失敗Windows引数長・引用符・Execution API経路の疑い機能群fixtureで分割診断する。
fixture全件成功機能群ごとのサーバー検証は成功巨大JSONを再送しない。Windows経路の制約として記録する。
fixture失敗対象群のサーバー経路または認証が未確認レスポンスの秘密値を出さず、action・suite・エラー種別だけで調査する。

4.1 JSONサイズ以外の回帰失敗を直した後の本番検証

必須の完了条件: 以前は通っていたローカル回帰テストが、WindowsのJSON引数長以外の理由で失敗した場合は、ローカル修正だけで完了にしない。関連するローカルテストと npm run prerelease を成功させ、承認済みリリース後に、影響した本番機能を必ず検証する。
  1. 失敗の原因を、実装・生成物・テストハーネス・環境に分類して記録する。
  2. ローカルで修正し、失敗したテスト、関連テスト、生成物同期、prereleaseを成功させる。
  3. 通常の承認済みリリース手順で対象コードを本番へ反映する。AIは承認なしにdeployしない。
  4. 影響した本番機能を確認する。既定は読取りまたはdry-runで、設定保存経路は該当fixtureを用いて writes=0 を確認する。
  5. 書込みでしか確認できない場合だけ、既存のDB操作手順に従い、operator承認・前後スナップショット・★テストデータ・後片付けをそろえる。

本番検証を行えない場合は「未検証」としてリリース状態に残し、修正完了・リリース完了とは扱わない。

5. 安全性の境界

  • fixture actionは読み取り・dry-runのみ。書込みactionを指定したfixtureはランナーが拒否する。
  • 成功条件は success=true、valid=true、writes=0 のすべて。
  • ランナーの標準出力は機能群名と件数だけ。設定値、メール本文、送信元、tokenを出力しない。
  • clasp run は本プロジェクトの承認対象であり、診断であってもoperatorの確認を経て実行する。
  • fixtureはGit管理対象にできるが、機密値を置かない。値を必要とする検証はローカルのgitignore設定経由に分離する。
